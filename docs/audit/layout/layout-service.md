# layout-service — layout audit

**Target:** service.html
**Findings:** 7

**Coverage notes:** Method: read the module's full CSS+HTML+JS (service.html, 3955 lines) and cross-referenced the EXACT shell-injected layers from the shell source (audit-www/index.html): injectUniformCSS global floors at :6074-6163 (text floor max(11px,1em); control floor min-height:44px !important on button/input/select/textarea in BOTH modes; td/th controls get min-width:0 relief but NOT min-height relief), the base MOBILE_CSS at :6178-6188 (table→block/scroll, inputs 16px, td 13px, buttons min-height:42px), the width @media 920/640 at :6093-6102 (fire in BOTH modes on any narrow viewport), and the per-module service block at :6210-6229 (grids→1col, stats-grid→2col, est-totals/tot-row/tot-input, cond/est table font/padding, table td input min-height:36px). All service-block and wizard rules are correctly scoped under html.bcc-mobile / [data-mod=\"service\"], so I found NO bcc-mobile leak into Desktop display and NO issue on the primary 1280xDesktop combo.

Screens walked (all 4 combos each — 360xMobile, 412xMobile, 1280xDesktop, plus 1280xMobile & 360xDesktop off-combos): dashboard (.dash-hero/.stats-grid/.svc-search-bar/.stage-chips/case-cards/pager); the 12-step New Order form (sec-0..sec-11 incl grid-2/3/4, check-columns, cond-table, est-table/est-totals, radio/check groups, watch-photo + after-photo, cash denomination grid, and the NEW Service Warranty (months) field #f-warr in the delivery grid-2 — it is covered by the grid collapse, no issue); the sidebar step rail (nav-0..nav-11) and mobile step-wizard + #form-wiznav; the follow-up overlay (.fu-overlay/.fu-modal/.fu-addform); proforma/job-card/GST-tax-invoice (print/report-engine only, rendered in the shell — not a viewport concern) and the CSV export buttons.

Notable NON-findings (verified OK): follow-up modal is solid — width:100%/max-width:520px, max-height:calc(100vh-96px), scrollable .fu-body with the action buttons INSIDE the scroll area, and .fu-addform collapses to 1col at ≤640, so no off-screen footer / no P0. Save is reachable on every wizard step (topbar + bottom-actions row are not .form-section children, so the wizard never hides them). cond-table/est-table are wrapped in .tbl-scroll and also get the shell table-scroll base rule, so wide tables scroll rather than clip. case-name has ellipsis; case-meta wraps. No fixed px min-width on any modal/card that exceeds 360 (fu-modal is width:100%). Grids collapse via BOTH the service block (class) and the module's own 720px @media (width).

Needs live-browser/device confirmation (static analysis only): (l1) the exact overflow/crush of the 2-column deno grid at 360xDesktop — depends on box-model rounding of the flex 52px+96px cells vs available width; (l2) whether a real-world revenue total actually exceeds the 2-col tile width and clips (depends on seeded/entered data magnitude and rendered font metrics); (l3) exact number of wrapped rows the 8 44px stage chips produce at 360/412; (l4/l5/l6) the 1280xMobile and 360xDesktop off-combos are unusual mode/width mismatches — confirm on a device only if those states are reachable via the Settings Display toggle at those widths. Could not run a live browser here (read-only static audit), so all wrap/clip/overflow claims are structural inferences from the CSS box model and the confirmed injection order.

## [P2] svc-l1 — Cash-denomination grid stays 2-column at narrow Desktop width (collapse gated on class, not width)
- **Module/area:** service | **Confidence:** medium | **Combo:** 360xDesktop
- **Location:** service.html:1219-1220 (#f-deno-wrap .deno-body) — step 11 Delivery, Payment Mode = Cash
- **Defect:** The denomination grid base is `#f-deno-wrap .deno-body{display:grid;grid-template-columns:1fr 1fr}` and the single-column collapse is `html.bcc-mobile #f-deno-wrap .deno-body{grid-template-columns:1fr}` — gated ONLY on the bcc-mobile CLASS, with no width @media. In the Desktop-display-at-360 off-combo (bcc-mobile absent, narrow viewport) the grid stays 2-column. Each cell is `.deno-lbl{flex:0 0 52px}` + `.deno-inp` + `.deno-val{flex:0 0 96px}`; two columns need ~2×(52+96)=296px of fixed width plus two inputs and an 18px column gap, but the available width in `.form-content` (padding 24/28px) minus `.deno-body` padding (14px×2) is ~300px, so the two `.deno-inp` inputs are crushed toward min-width:0 and the fixed ₹-value/label cells risk horizontal overflow.
- **Evidence:** #f-deno-wrap .deno-body{...grid-template-columns:1fr 1fr}  /*base*/  +  html.bcc-mobile #f-deno-wrap .deno-body{grid-template-columns:1fr}  /*only class-gated, no width @media*/
- **Impact:** In the off-combo where the app is in Desktop display on a ~360px screen, the physical-cash-counting grid at delivery is squashed to near-unusable input widths and may overflow. Real Mobile display is fine (collapses to 1col); pure 1280 Desktop is fine. Optional grid (Cash only), so scoped impact.
- **Fix hint:** Add a width-based fallback so the collapse also fires when narrow regardless of class, e.g. `@media(max-width:640px){#f-deno-wrap .deno-body{grid-template-columns:1fr}}` alongside the existing class rule. CSS-only, additive, no storage/library change.

## [P2] svc-l2 — Est. Revenue stat value can be clipped (overflow:hidden card, no wrap/ellipsis) for long rupee sums
- **Module/area:** service | **Confidence:** medium | **Combo:** 360xMobile
- **Location:** service.html:146-186 (.stat-card / .stat-value / .stat-value.gold) — dashboard stats-grid, 'Est. Revenue' tile #st-rv
- **Defect:** `.stat-card{overflow:hidden}` and `.stat-value{line-height:1}` have no `word-break`, `overflow-wrap`, or ellipsis. The Est. Revenue tile renders `'₹' + rev.toLocaleString('en-IN')` (renderDash, service.html:2533) which for a realistic all-cases total can be 8-10 chars (e.g. ₹12,34,567). On mobile the service MOBILE_CSS keeps `.stats-grid` at 2 columns (index.html:6217) and the module shrinks `.stat-value.gold` to 18px (service.html:1148), so the tile is ~150-160px wide; a long tabular-nums figure exceeds that width and is silently clipped by the card's `overflow:hidden`.
- **Evidence:** .stat-card{...overflow:hidden;} .stat-value{font-size:32px;line-height:1;font-variant-numeric:tabular-nums} .stat-value.gold{font-size:22px}  — no word-break/ellipsis; JS: st-rv = '₹'+rev.toLocaleString('en-IN')
- **Impact:** The headline revenue KPI can be visually truncated (e.g. shows '₹12,34,5' cut off) on a phone once the shop has meaningful turnover, giving a wrong/incomplete number at a glance.
- **Fix hint:** Allow the value to shrink/wrap: on `.stat-value` add `overflow-wrap:anywhere` (or reduce `.stat-value.gold` font at ≤640 and/or `white-space:nowrap;text-overflow:ellipsis` with a title tooltip). Optionally use a shorter compact format. CSS-only.

## [P2] svc-l3 — Repair-stage filter chips are <button>s inflated to 44px by the shell control-floor, producing a tall multi-row filter block on mobile
- **Module/area:** service | **Confidence:** medium | **Combo:** 360xMobile
- **Location:** service.html:391-396 (.stage-chip) rendered as <button> in renderStageChips (service.html:2513-2519); shell floor index.html:6141-6151
- **Defect:** Each stage chip is emitted as `<button class="stage-chip">` (service.html:2514). The shell's unconditional control floor forces `html body button{min-height:44px !important;min-width:44px}` (index.html:6149-6150) in BOTH modes. The chips are designed as compact pills (`padding:5px 12px;font-size:12px`) but are lifted to 44px tall each. renderStageChips outputs 8 chips (All stages, 5 stages, Overdue, Follow-up due) into `.stage-chips{display:flex;flex-wrap:wrap}`. At 360px these wrap into roughly 3 rows of 44px-tall chips, consuming a large vertical band above the case list.
- **Evidence:** .stage-chip{font-size:12px;padding:5px 12px;...}  rendered as `<button class="stage-chip ...">`; shell: html body button{min-height:44px !important}
- **Impact:** The open-case pipeline filter row balloons vertically on phones, pushing the actual case list down; not broken but a meaningful density regression (checklist #7 — 44px floor bloating a chip row).
- **Fix hint:** Cannot lower the shell floor from the module. Mitigate by making the chip row horizontally scroll instead of wrap (e.g. `.stage-chips{flex-wrap:nowrap;overflow-x:auto;-webkit-overflow-scrolling:touch}` under ≤640) so the tall chips stay on one scrollable line, matching the tab-strip pattern the shell already uses. CSS-only.

## [P2] svc-l4 — 1280xMobile off-combo: the 12-step sidebar does not reflow (720px @media doesn't fire), stacking a full-height 220px navy rail above the wizard with its action buttons still showing
- **Module/area:** service | **Confidence:** medium | **Combo:** 1280xMobile
- **Location:** service.html:445-456 (.form-sidebar), :1067-1121 (@media max-width:720px reflow), :1115 (.sidebar-actions display:none); shell index.html:6212 (.form-layout display:block)
- **Defect:** In Mobile display the shell sets `html.bcc-mobile[data-mod="service"] .form-layout{display:block !important}` (index.html:6212) and the module activates the one-section step wizard (`html.bcc-mobile .form-content > .form-section{display:none}` service.html:1232). But the sidebar's reflow into a horizontal step-chip rail AND the hiding of `.sidebar-actions` live only in `@media(max-width:720px)` (service.html:1071-1115), which does NOT fire at a 1280 viewport. So at 1280xMobile the original vertical `.form-sidebar{width:220px;height:calc(100vh-60px);position:sticky;overflow-y:auto}` renders as a full-viewport-height 220px navy block stacked above the wizard, still showing the Save/Print/Back `.sidebar-actions` that are meant to be hidden on mobile.
- **Evidence:** .form-sidebar{width:220px;height:calc(100vh - 60px);position:sticky;top:60px}  ; reflow+hide only inside @media (max-width:720px){ .form-sidebar{...row...} .sidebar-actions{display:none} }  ; shell .form-layout{display:block !important}
- **Impact:** Mobile display on a wide (~1280) screen shows a large redundant navy sidebar column occupying the first screen before the wizard, plus duplicate Save/Print/Back controls. Degraded but functional (wizard works below). Off-combo (mobile mode on desktop-width), so lower priority.
- **Fix hint:** Gate the sidebar reflow + `.sidebar-actions{display:none}` on the mobile CLASS too, not only the 720px width — e.g. duplicate the reflow rules under `html.bcc-mobile .form-sidebar {...}` / `html.bcc-mobile .sidebar-actions{display:none}` so they hold at any width in Mobile display. CSS-only.

## [P3] svc-l5 — Desktop-display at narrow width shows all 12 form sections at once (wizard is class-gated), yielding one very long scroll
- **Module/area:** service | **Confidence:** high | **Combo:** 360xDesktop
- **Location:** service.html:1232-1234 (html.bcc-mobile step wizard), :1237 (#form-wiznav), :1067-1121 (720px reflow)
- **Defect:** The one-section-at-a-time wizard and the sticky bottom `#form-wiznav` are gated on `html.bcc-mobile` (service.html:1232,1237), so in the Desktop-display-at-360 off-combo they are inactive and every `.form-section` (all 12) renders stacked. The 720px @media does reflow the sidebar into a chip rail and `scrollToSec` falls back to smooth-scroll (isMobileWiz() reads the absent class), so navigation still works, but the New Order form becomes a single multi-thousand-pixel scroll.
- **Evidence:** html.bcc-mobile .form-content > .form-section{display:none}  /*wizard only under the class*/  ; #form-wiznav{display:none} html.bcc-mobile #form-wiznav{display:flex}
- **Impact:** Heavy scroll on a narrow Desktop-mode screen; navigable via the chip rail so not blocking. Off-combo and low severity.
- **Fix hint:** Optionally gate the wizard on width too (e.g. also activate single-section mode under `@media(max-width:720px)`), or accept as intended desktop-narrow behavior. CSS-only if changed.

## [P3] svc-l6 — Back-home FAB sits just above the sticky wizard bar on mobile, crowding the 'Next ›' control

- **Location:** shell index.html:6031/6039 (#st-v5-home-fab bottom:84px→76px mobile, right:14px, z-index max); service.html:1238 (#form-wiznav sticky bottom:0 z-index:50, wiz-next at right)

The FAB floats over the region immediately above the bar on the right side; depending on exact bar height it visually crowds the Next button. ## [P3] svc-l7 — Toast wrap/max-width fix is width-gated (≤640), so a long toast stays nowrap in Mobile display on wider screens
- **Module/area:** service | **Confidence:** low | **Combo:** 1280xMobile
- **Location:** service.html:906-924 (.toast{white-space:nowrap}), :1213-1214 (@media max-width:640 → white-space:normal; max-width:calc(100vw-32px))
- **Defect:** The base `.toast{white-space:nowrap}` with the wrap+clamp fix only inside `@media(max-width:640px)`. In the Mobile-display-at-1280 off-combo the 640 media is off, so a long message (e.g. the duplicate-customer notice 'ℹ Existing customer — N prior cases on this mobile', service.html:2293) stays a single non-wrapping centered line. - **Evidence:** .toast{...white-space:nowrap}  ; @media (max-width:640px){ .toast{ max-width:calc(100vw - 32px); white-space:normal } }
- **Impact:** Negligible in practice; a long toast could overflow at mid widths in Mobile display. Cosmetic edge case.
- **Fix hint:** Move the toast `max-width:calc(100vw-32px)` / `white-space:normal` out of the width @media (or also apply under `html.bcc-mobile .toast`) so it holds at any Mobile width. CSS-only.
