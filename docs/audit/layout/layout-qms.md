# layout-qms — layout audit

**Target:** qms.html
**Findings:** 11

**Coverage notes:** Static CSS/JS audit only; no live browser/device run. All four combos were reasoned about. The module is genuinely well-built for mobile in most respects: modals use the correct flex-column + max-height:90vh + scrollable body + fixed footer pattern (footer never off-screen — no P0 modal defect), every table is wrapped in .tbl-wrap with overflow-x:auto and a sticky identity column, grids collapse to 1col via an !important rule at <=640, the CRO Master table card-reflows, and inputs are 16px to avoid iOS zoom.\n\nThe REAL risks all stem from ONE architectural choice: the module's responsive layer is gated on @media(max-width:640px) (a WIDTH query) while the shell's chrome is gated on the html.bcc-mobile CLASS. NEEDS LIVE/DEVICE CONFIRMATION:\n(1) L01 double-hamburger — must confirm on device whether the shell actually injects #st-v5-qms-menu when the module already ships .qms-menu-btn, and their relative z-index/overlap. This is the highest-value item to verify.\n(2) L02 & L04 — the 1280xMobile empty-gutter and the 641-800px 'hidden sidebar, no visible ☰' band depend on exactly what the shell's injected bcc-mobile[data-mod=qms] rules set for .sidebar transform and whether they also zero --sidebar / .main-area margin. I could only read the pipeline summary (translateX(-240px), .open slides in) — the shell source was not provided, so confidence is medium. Confirm whether shell also resets margin-left / --sidebar and whether its ☰ shows at all widths when bcc-mobile is on.\n(3) L03 drawer-doesn't-close is confirmed from source (no qmsNavToggle uncheck anywhere) — high confidence, but worth a quick device tap-through.\n(4) L10 inline 📞/📲 button 44px bloat depends on the shell floor's exact specificity vs the inline style — confirm rendered height in devtools.\nItems L05-L09, L11 are cosmetic/polish. No data-loss, no unreachable-submit, no clipped-with-no-scroll (P0) defects were found; the two P1s (L01, L03) and the mode/width mismatch P1 (L02) are the priority fixes. All fix hints are additive CSS/JS within qms.html and obey the read-only/offline/no-new-lib rules.

## [P1] qms-L01 — Two hamburger buttons overlap top-left in Mobile display (module's own ☰ + shell-injected ☰)
- **Module/area:** qms | **Confidence:** high | **Combo:** 360xMobile, 412xMobile
- **Location:** qms.html lines 258-265 (.qms-menu-btn) + shell-injected #st-v5-qms-menu (INJECTION_PIPELINE.md line 36)
- **Defect:** The module ships its OWN CSS-only off-canvas drawer: an <input id=qmsNavToggle> checkbox + a fixed ☰ button .qms-menu-btn at top:9px;left:10px;z-index:60;width:44px;height:44px (shown by @media(max-width:640px)). The shell ALSO injects its own QMS off-canvas menu button #st-v5-qms-menu + scrim #st-v5-qms-scrim under html.bcc-mobile[data-mod='qms']. In Mobile display at any width <=640 BOTH fire simultaneously, so two identical navy ☰ buttons stack on top of each other in the top-left corner.
- **Evidence:** .qms-menu-btn{display:flex;...position:fixed;top:9px;left:10px;z-index:60;width:44px;height:44px;...} at line 258-264, shown by @media(max-width:640px); shell injects #st-v5-qms-menu ☰ + #st-v5-qms-scrim for data-mod=qms mobile per INJECTION_PIPELINE.md line 36-37.
- **Impact:** Confusing double control; depending on injected z-index one ☰ is dead/covered. The two drawers are driven by different mechanisms (module = :checked sibling selector setting translateX(0); shell = a .open class), so tapping one button may open the sidebar while the other button's tap does nothing, and the two overlays (.qms-nav-overlay at z-index:35 vs #st-v5-qms-scrim) can fight. User sees a stuck/duplicate menu affordance.
- **Fix hint:** Suppress ONE of the two drawers in Mobile display. Cleanest additive fix inside qms.html: hide the module's own control when the shell's is present — add `html.bcc-mobile .qms-menu-btn,html.bcc-mobile .qms-nav-overlay,html.bcc-mobile #qmsNavToggle{display:none!important}` so only the shell-injected off-canvas runs in Mobile mode, and let the module's own @media drawer serve only the Desktop-at-narrow-width mismatch (bcc-mobile absent). Verify on device which drawer the shell actually wires.

## [P1] qms-L02 — Mobile display at wide viewport (1280xMobile): sidebar pushed off-canvas by shell but --sidebar stays 240px, leaving a 240px empty gutter with no visible nav
- **Module/area:** qms | **Confidence:** medium | **Combo:** 1280xMobile
- **Location:** qms.html line 64 (.main-area margin-left:var(--sidebar)) + line 41 (.sidebar) vs shell bcc-mobile[data-mod=qms] sidebar translateX(-240px)
- **Defect:** The module's own responsive layer that zeroes --sidebar and shows the ☰ is gated on @media(max-width:640px) (line 249) — WIDTH based, not bcc-mobile. At 1280px in Mobile display, that media query does NOT fire, so :root keeps --sidebar:240px, .main-area keeps margin-left:240px, and .qms-menu-btn stays display:none (base rule line 247). BUT the shell, under html.bcc-mobile[data-mod=qms], transforms .sidebar translateX(-240px) (pushed off-screen) per pipeline line 37. Net result: sidebar is invisible (translated off) yet .main-area is still indented 240px, producing a large empty left gutter and no on-screen way to reach nav unless the shell's injected ☰ handles it.
- **Evidence:** .main-area{margin-left:var(--sidebar)} (line 64), :root{--sidebar:240px} (line 32); the zero-out lives only under @media(max-width:640px){:root{--sidebar:0px}} (line 251) which does not fire at 1280; shell pushes .sidebar translateX(-240px) under bcc-mobile[data-mod=qms] (INJECTION_PIPELINE.md line 37).
- **Impact:** Content shifted right with a dead 240px band; if the shell's injected ☰ isn't shown/working at this width the sidebar nav is entirely unreachable. Cosmetically broken layout for anyone forcing Mobile mode on a wide screen/tablet-landscape.
- **Fix hint:** Add a bcc-mobile-scoped rule (not width-gated) that mirrors the drawer setup: `html.bcc-mobile{--sidebar:0px}` and `html.bcc-mobile .main-area{margin-left:0}` plus `html.bcc-mobile .qms-menu-btn{display:flex}` (or rely on the shell ☰ if it renders at all widths). This makes the off-canvas layout follow the mode class rather than only the 640px width query.

## [P1] qms-L03 — Mobile nav drawer does not auto-close after selecting a nav item (checkbox never unchecked)
- **Module/area:** qms | **Confidence:** high | **Combo:** 360xMobile, 412xMobile, 360xDesktop
- **Location:** qms.html line 335 (#qmsNavToggle checkbox) + nav-item buttons lines 345-354 (onclick=switchView) + switchView line 429
- **Defect:** The module's off-canvas sidebar is opened by checking #qmsNavToggle. Each .nav-item calls switchView(name) which swaps the view but there is NO code (and no CSS) that unchecks #qmsNavToggle. So after a user taps a menu entry, the drawer + its full-screen .qms-nav-overlay (z-index:35) remain open, covering the view they just navigated to. The user must manually tap the overlay or ☰ to dismiss it every single time.
- **Evidence:** <input type=checkbox id=qmsNavToggle class=qms-menu-toggle> (line 335); nav-items only do onclick=switchView('x') (lines 345-354); switchView() (line 429) touches .view/.nav-item classes only — no reference to qmsNavToggle anywhere in the script (grep confirmed 0 hits).
- **Impact:** Every navigation on mobile leaves the freshly-selected screen hidden behind the open drawer + dark overlay until a second manual dismiss tap. Makes the primary nav flow feel broken on phones.
- **Fix hint:** Add `document.getElementById('qmsNavToggle')?.removeAttribute('checked')` — actually set .checked=false — inside switchView(), e.g. `var _t=$('qmsNavToggle');if(_t)_t.checked=false;` at the top of switchView. Additive, no new libs.

## [P2] qms-L04 — Off-canvas drawer + grid collapse keyed to @media(max-width:640px), not to bcc-mobile — 412px large phones fine, but the mode/width decoupling is fragile
- **Module/area:** qms | **Confidence:** medium | **Combo:** 360xMobile, 412xMobile, 1280xMobile
- **Location:** qms.html line 249 @media(max-width:640px){...} whole mobile layer
- **Defect:** The ENTIRE module mobile layer (drawer, --sidebar:0, grid->1col collapse via line 271, kpi 2-up, table min-width, CRO card reflow, 16px inputs) is gated on max-width:640px. The shell's mode is a CLASS (bcc-mobile) that can be ON at widths >640 (combo 1280xMobile) or OFF at widths <640 (combo 360xDesktop). At 360xDesktop the width query still fires so the module coincidentally renders mobile-correctly; but at 1280xMobile the module renders its DESKTOP layout (6-col KPI, 2-col grids, full sidebar assumption) while the shell applies mobile chrome — see L02. The 641-800px band is also handled only by the coarser @media(max-width:800px) desktop block (sidebar translateX(-240px) but NO ☰ button shown, since .qms-menu-btn only appears at <=640) — so 641-800px Desktop display has a hidden sidebar with no visible opener.
- **Evidence:** Mobile layer @media(max-width:640px) at line 249; the 800px block line 223 sets .sidebar{transform:translateX(-240px)} and depends on .sidebar.open (never toggled — grep shows no classList.add('open') / no .open toggling JS); .qms-menu-btn base display:none (line 247) only overridden inside the 640px query.
- **Impact:** Sidebar unreachable in the 641-800px Desktop band (no ☰ shown, sidebar translated off, .sidebar.open class never added by any JS). Mismatch combos rely on width coincidence rather than the mode class, so behavior is inconsistent.
- **Fix hint:** Either raise the module drawer/collapse breakpoint to match the shell's 800px sidebar-hide (show .qms-menu-btn up to 800px), or better, scope the mobile layer under html.bcc-mobile in addition to the width query so mode drives it. Also give the 641-800px range a visible ☰. Additive CSS only.

## [P2] qms-L05 — Live Queue / Dashboard queue cards: grid-auto minmax(300px,1fr) can overflow at 360 before the mobile 1-col override; long customer names and ₹ have no ellipsis
- **Module/area:** qms | **Confidence:** medium | **Combo:** 360xMobile, 360xDesktop
- **Location:** qms.html line 101 (.grid-auto minmax(300px,1fr)) + line 549 queueCard, collapse at line 271
- **Defect:** .grid-auto uses repeat(auto-fill,minmax(300px,1fr)). The module's own @media(max-width:640px) forces it to 1fr (line 271, with !important) and adds .grid-auto>*{min-width:0} (line 286), so at <=640 cards collapse to one column — good. HOWEVER the 300px min-track means at exactly ~360 the card content area is ~330px; the queueCard .q-name (font-size 15px) and the tag row (.q-tags with Entry time, Wait badge, CRO name badge, priority badge, 'Purchased in DSR' badge) can be a long flex-wrap row. A long customer name in .q-name has no white-space/ellipsis handling; a very long name pushes card width. In the mismatch 360xDesktop combo the width query DOES fire so it collapses, so risk is limited to content wrap, not layout break.
- **Evidence:** .grid-auto{grid-template-columns:repeat(auto-fill,minmax(300px,1fr))} line 101; .q-name{font-size:15px;font-weight:700} line 149 (no text-overflow); q-tags flex-wrap line 151; queueCard badges built at line 549.
- **Impact:** Cards wrap acceptably but long names/many badges make cards tall and ragged; no truncation on .q-name or CRO-name badges. Minor visual, not a blocker.
- **Fix hint:** Add `.q-name{overflow-wrap:anywhere}` and consider `.q-tags .badge{max-width:100%;overflow:hidden;text-overflow:ellipsis}`. Keep the min-width:0 relief. Cosmetic, low risk.

## [P2] qms-L06 — 16px input font + 44px control floor bloat the dense 2-col form-grid in Customer Entry / Close Lead on narrow screens

## [P2] qms-L10 — Inline tel/WhatsApp contact buttons inside table cells get forced to 44px min-height by shell floor, distorting dense follow-up/preclaim rows
- **Module/area:** qms | **Confidence:** medium | **Combo:** 360xMobile, 412xMobile, 1280xDesktop
- **Location:** qms.html line 567 contactBtns (a.btn.xs + button.btn.xs at padding 2px 7px) used in lines 549/558
- **Defect:** contactBtns emits an <a class='btn xs ghost' style='padding:2px 7px'>📞</a> and a <button class='btn xs ghost' style='padding:2px 7px'>📲</button> inline next to the mobile number inside table cells (Follow-ups, and appended after mobile in queue cards). The shell control floor forces min-height:44px!important on a.btn/button. Inside a td the shell gives min-width:0 relief but NOT min-height relief, so these tiny inline 2px-padded icons become 44px tall, vertically bloating the follow-up table rows and the .q-meta line in queue cards (where they sit inline with text at line 549), misaligning the number/visit-type text.
- **Evidence:** contactBtns returns `<a class="btn xs ghost" style="...padding:2px 7px" ...>📞</a><button class="btn xs ghost" style="padding:2px 7px" ...>📲</button>` line 567; shell floor min-height:44px!important with only min-width:0 relief for td descendants (INJECTION_PIPELINE.md line 28); used inline in queueCard .q-meta (line 549) and Follow-ups mobile cell (line 558).
- **Impact:** The 📞/📲 chips balloon to 44px tall inline, breaking the baseline of the mobile number line in queue cards and inflating follow-up table row height. Vertical misalignment; not a blocker.
- **Fix hint:** These inline contact controls need a min-height override the shell floor won't beat easily; since !important is on the floor, add an equally-specific `.q-meta .btn.xs,.tbl td .btn.xs{min-height:0!important}` scoped tight to these inline chips (they are already big enough tap targets via padding? no — 2px padding is below 44px, so instead give them width/height 32px explicitly and accept a slightly-below-floor tap area, or move them to their own row). Verify on device.

## [P3] qms-L08 — Audit Trail detail cell dumps raw JSON.stringify with no wrap/overflow guard; long payloads can widen the audit row
- **Module/area:** qms | **Confidence:** medium | **Combo:** 360xMobile, 412xMobile
- **Location:** qms.html line 568 (.audit-detail JSON.stringify(a.details))
- **Defect:** In renderReports the Audit Trail prints `esc(JSON.stringify(a.details||{}))` inside .audit-detail (font-size 11px). Some audit details include croName, queueNo, reason strings; a long stringified object is an unbroken token-ish string. .audit-detail has no overflow-wrap/word-break. The parent .card-body has max-height:400px;overflow-y:auto (vertical only), so horizontal overflow is not scrollable there.
- **Evidence:** `<div class="audit-detail">${esc(JSON.stringify(a.details||{}))}</div>` at line 568; .audit-detail{font-size:11px;color:var(--muted)} line 197 (no wrap); card-body max-height:400px;overflow-y:auto (no overflow-x) line 568.

## [P3] qms-L11 — Toast max-width:90vw and bottom:28px can collide/overlap with the shell back-home FAB at the bottom in Mobile
- **Module/area:** qms | **Confidence:** low | **Combo:** 360xMobile, 412xMobile
- **Location:** qms.html line 198 (.toast position:fixed;bottom:28px;z-index:999)

- **Evidence:** .toast{position:fixed;bottom:28px;left:50%;...z-index:999;max-width:90vw} line 198; shell adds body{padding-bottom:72px} / mobile 80px + back-home FAB (INJECTION_PIPELINE.md lines 18,33,60).
- **Impact:** Transient visual overlap of toast and the shell bottom FAB; toast is on top so message stays readable. Minor, time-limited.
- **Fix hint:** Raise toast bottom offset on mobile (e.g. `html.bcc-mobile .toast{bottom:92px}`) to clear the FAB zone. Cosmetic.
