## 1. THE decisive architectural constraint (kills per-value-on-read designs)

Every consumer reads synchronously: `SP.getItem = function(k){ return _ready ? (MEM.has(...)? MEM.get(...) : null) : nGet... }` (storage-core.js:225). WebCrypto has no sync API. Therefore **MEM must always hold PLAINTEXT**; decrypt-on-read / encrypt-on-write inside setItem/kvUpsert (both sync, :226-233, :85-89) is impossible without breaking the app's entire sync contract. The only viable encryption seam is the ASYNC persist/boot boundary:

- ENCRYPT: inside `persist()` between `db.export()` (:177) and `FS.writeFile` (:182) — note :177 is currently sync try/catch; encryption makes the b64 production async, so the mutex (`_persisting` :173) must extend across the awaited encrypt.
- DECRYPT: inside `rd()` (:306) before `open(bytes)`.

This is "whole-file envelope encryption" — the SQLite blob is encrypted as one unit; kv values inside are untouched.

## 2. Migration design space (in place, existing plaintext)

**Option W — whole-file envelope (RECOMMENDED): migration cost ≈ one ordinary persist.** No data rewrite at all. First encrypted-build boot: `rd()` reads a plaintext bcc.sqlite (detect: SQLite magic bytes `"SQLite format 3\0"` vs an `SBCC1` envelope header), opens it as-is, and the very next `persist()` writes ciphertext. The existing `.bak` rotation naturally ages out plaintext (.bak lags live by one, :181), and the plan should force one `flush()` + one follow-up persist after first encrypted boot so live AND .bak are both ciphertext, then done. **Chunked vs big-bang is a non-question in Option W** — there is no per-key rewrite, so the QMS-ANR lesson is satisfied for free: encryption of a 10 MB blob via `crypto.subtle.encrypt` (AES-GCM) is one async call, and the only remaining sync main-thread costs are the ones that already exist today (`db.export()` + `bytesToB64`, already flagged heavy at :63 and :395-398 — encryption adds no new sync serialize).

**Option V — per-value ciphertext in kv (NOT recommended, mapped for completeness).** Values become `enc1:<iv>:<b64ct>`; MEM stays plaintext; kvUpsert encrypts... but kvUpsert is sync (:87) → you'd need a shadow async pipeline (dirtyKeys-style), a chunked first-boot migration (~3,300 keys; :218 "3,300 keys → multi-second stalls" is the measured scale) run in idle slices under `bulkAsync` (:399-407) to avoid the per-chunk export ANR (:395-398 documents exactly this force-close). Mixed-state hazards below make this strictly worse than W for no gain (the file is app-private either way; per-value only helps if you wanted selective/lazy decryption, which the sync read contract forbids anyway).

## 3. The mixed plaintext/ciphertext resurrection question (asked directly)

Yes, under Option V a half-migration + crash + `.bak` recovery ABSOLUTELY produces a mixed store: `.bak` is one persist behind (:181), and the recovery chain (:313-322) will happily adopt it; additionally `replayWAL` (:146-161) re-applies pre-migration WAL entries whose `op.v` is PLAINTEXT into the db — so even the live file can be re-polluted with plaintext values AFTER a "migrated-to-encrypted" flag was set. Conclusion: **any per-value scheme MUST use a per-VALUE format marker (self-describing `enc1:` prefix), never a per-store marker.** A per-store marker is provably wrong in this codebase because three independent replayers (WAL replay :146, .bak adoption :318, catastrophic native-LS re-migration :279-283) can each inject plaintext after the marker is set. With per-value markers, mixed state is benign (reader branches on prefix; migration is idempotent and resumable). Under Option W the same rule applies at file granularity: the READER must sniff the header (SQLite magic vs envelope) rather than trust any marker — then live=cipher/.bak=plain, live=plain/.tmp=cipher, every crash combination is self-healing. **Do not gate decryption on a `saagar_storage_encrypted` flag; gate on file content.**

## 4. Rollback (`STORAGE_CORE_ENABLED=false`) — the recipe changes

Critical pre-existing fact the wave must state honestly: flag-off rollback is ALREADY lossy today, independent of encryption. Flag off → storage-core returns at :33 → app runs on NATIVE localStorage → which is the frozen first-C-boot snapshot (sets never propagated, :240 "sets stay MEM-only"). Everything written since the first C-boot lives only in bcc.sqlite/MEM. sqlite-store.js then wakes up (its stand-down guard :29 no longer fires), does its Design-A `reconcile()` (sqlite-store.js:123-148): keys in the DB but missing from native LS are hydrated back (:131-137) — **this is the accidental rollback-recovery path, and it reads bcc.sqlite RAW (sqlite-store.js:158-162, no decrypt, only a naive `new SQL.Database(bytes)` with try/catch fresh-fallback :161-162).** So once bcc.sqlite is encrypted, flag-off drops the user to the stale native snapshot AND sqlite-store silently starts a FRESH db ("open existing DB failed... starting fresh") — then its write-through would eventually OVERWRITE the encrypted file with a plaintext DB built from stale native LS. That is the mixed/rollback brick scenario to design against.

**Rollback recipe that must be shipped as part of R0-W2:**
1. Primary rollback = a DECRYPT-IN-PLACE step, not just the flag: on a rollback build (or a maintenance toggle), boot normally (decrypting reader), then persist once with encryption disabled → file returns to plaintext → THEN flag-off behaves exactly as today. Because the reader is header-sniffing (§3), an old encrypted-capable build can always read back a plaintext file, so this is reversible in both directions.
2. Secondary rollback (device can't boot the encrypted build at all) = restore from the plaintext JSON backups: auto-backup.js snapshots via `localStorage.getItem` (auto-backup.js:63-67) which routes through SP.getItem → MEM → **plaintext**, so `Documents/SaagarBCC-Backups/backup-YYYY-MM-DD.json` + `latest.json` remain valid flag-off restore material regardless of DB encryption. Same for manual `backupPayload()` (index.html:5670) / `restoreValidatedBackup()` (index.html:5923, which uses `SaagarStore.bulk` :5944). R0-W2 must NOT touch these paths (R0-W3 hardens them).
3. sqlite-store.js needs a one-line-class guard in the SAME wave (encrypted-header sniff → stand down / refuse to open+overwrite) so the flag-off + encrypted-file combination can never clobber the ciphertext with a stale plaintext DB. This is the only edit outside storage-core the migration strictly requires.

## 5. Residual plaintext channels (scope honesty for the build contract)

Encrypting bcc.sqlite alone leaves, by design in this wave:
(a) native localStorage frozen snapshot — a full plaintext copy of all data as of first C-boot, kept deliberately as the catastrophic-recovery source (:279-283; deleting it removes the last-ditch net — a policy decision for the owner, not a code default);
(b) the WAL (`saagar_storage_wal`, native LS) carries plaintext values up to 50 KB inline (:116) between write and persist — sync-write requirement (nSet at :129) makes WebCrypto-encrypting it impossible; window is bounded by SAVE_DEBOUNCE 6 s (:63) + WAL clear at :184; document as accepted residual or force `big:1` pointer-mode for sensitive keys (cost: a forced persist per write, ANR risk — recommend accept-and-document);
(c) daily plaintext JSON in shared `Documents/` (auto-backup.js:90-94, DOCUMENTS dir — WORLD-readable relative to DATA) — the single largest real-world exposure, bigger than bcc.sqlite; belongs to R0-W3 but must be named now;
(d) WebView localStorage backing files (Android profile dir) hold (a)+(b) on disk. `allowBackup=false` already blocks ADB/cloud extraction of DATA.

## 6. Key custody (facts only)

No Keystore-backed plugin exists (package.json: filesystem/app/core/notifications/share only) and "no new libs" forbids adding `@capacitor/preferences` or a secure-storage plugin — so the key must be derived/stored with what exists: a random 256-bit key generated once, stored as a file in DATA (dies with uninstall AND factory reset — matches `allowBackup=false` semantics; APK re-install = data gone anyway since DATA is wiped, so "survive reinstall" is moot for the file store) — OR derived from the owner PIN (survives via backup restore but creates the encrypted-at-rest vs available-at-boot deadlock: boot needs data before PIN entry; the shell reads MEM at startup). Fail-open posture consistent with the codebase (every layer here fails open, :20, :344): **random device-local key file in DATA, non-extractable CryptoKey imported at boot; if the key file is missing but the DB is encrypted → treat as corrupt → recovery chain → native-LS re-migration (:279) saves the data.** That keeps availability primacy and makes key loss non-fatal — at the cost that the threat model is "data at rest unreadable if DATA files are copied off a non-rooted path", not "protected from an attacker with full DATA access". State this honestly to the owner before build.
