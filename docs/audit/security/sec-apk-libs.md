# sec-apk-libs — security audit

**Target:** AndroidManifest/capacitor/bundled libs
**Findings:** 5

**Coverage notes:** READ-ONLY audit; no files edited. Target app = saagar-control-centre (com.saagartraders.bcc), the demo dir was ignored. BUILD IDENTITY: only DEBUG merged/packaged manifests exist under android/app/build/intermediates/ (no release variant). The seeded/distributed APK (SaagarCC-DemoData-V6-Wave3.apk) is therefore a debug build, which is why the merged manifest injects android:debuggable="true" (line 27 of android/app/build/intermediates/merged_manifests/debug/AndroidManifest.xml) even though the source manifest does not set it.

WEBVIEW POSTURE (GOOD): MainActivity.java is a bare `BridgeActivity{}` — no custom WebView config, no addJavascriptInterface, no setAllowFileAccess/setAllowUniversalAccessFromFileURLs overrides. Capacitor 6.2.1 defaults apply: content served over https://localhost via WebViewAssetLoader (androidScheme=https, hostname=localhost), NOT file://, so file-scheme SOP-bypass classes don't apply. capacitor.config.json: allowMixedContent=false, webContentsDebuggingEnabled=false, captureInput=true, CapacitorHttp disabled. No usesCleartextTraffic / networkSecurityConfig set (fine — no cleartext traffic exists). server.allowNavigation unset → navigation locked to localhost. android/app/src/main/res/xml/config.xml has legacy Cordova `<access origin="*"/>` but Capacitor ignores config.xml for navigation — INERT, not a finding.

EXPORTED COMPONENTS: MainActivity exported=true with LAUNCHER filter (required, safe). FileProvider exported=false. Notification plugin (@capacitor/local-notifications 6.x) added receivers TimedNotificationPublisher + NotificationDismissReceiver with NO explicit android:exported, but they carry no intent-filter so Android defaults them to exported=false → SAFE. LocalNotificationRestoreReceiver is exported=false with BOOT_COMPLETED filter (safe, standard). androidx ProfileInstallReceiver exported=true but permission-gated by android.permission.DUMP (framework component, safe). New permissions from plugin: RECEIVE_BOOT_COMPLETED, WAKE_LOCK, POST_NOTIFICATIONS — all legitimate for scheduled reminders. No needlessly-exported component found.

INTERNET: app is genuinely offline — grep of www/index.html + saagar-report.js shows zero fetch/XHR/WebSocket to any remote host; only tel: and https://wa.me/ links (OS-handled external intents that do NOT require the app to hold INTERNET). The <uses-permission INTERNET> in the source manifest is thus UNUSED surface (see sec-apk-2).

BUNDLED LIBRARY VERSIONS + CVE VERDICTS:
- jsPDF 2.5.2 (banner: "Version 2.5.2 Built on 2024-09-17", www/jspdf.umd.min.js line 5) — CLEAN. No known exploitable CVE in 2.5.2 for this offline, self-generated-content use.
- jsPDF-AutoTable v5.0.8 (www/jspdf.plugin.autotable.min.js line 3) — CLEAN, no known CVE.
- JSZip 3.10.1 (banner line 4, www/jszip.min.js) — the JSZip path-traversal advisory (GHSA-jg8v..., fixed in 3.7.0) is FIXED in 3.10.1. Also only ever used to GENERATE zips (salary-slip ZIPs via zip.file()/generateAsync in saagar-report.js) — never to extract untrusted archives. CLEAN.
- html2canvas 1.4.1 (banner line 2) — latest release; no known exploitable CVE. CLEAN.
- pdf.js 3.11.174 (apiVersion:"3.11.174" embedded in www/pdf.min.js) — this version IS < 4.2.0 so technically in the CVE-2024-4367 (crafted-PDF FontMatrix → arbitrary JS) affected range. NOT REACHABLE / NOT EXPLOITABLE here: the ONLY getDocument() call site is saagar-report.js:1456-1458 (`pdfjsLib.getDocument({url:url})`), where `url` is `URL.createObjectURL(blob)` (line 1429) and every caller feeds a blob the app JUST generated in-process via jsPDF (renderDoc(...).output('blob')). There is NO path to open an externally-supplied/attacker-crafted PDF: the app is fully offline and the only <input type=file> (index.html:1425) accepts application/json,.json only. So the malicious-PDF vector cannot reach the vulnerable code. Verdict: affected-version-but-unreachable → informational (sec-apk-5).
- sql.js / sql-wasm.js — version NOT embedded in the bundled emscripten file and sql.js is not in node_modules, so exact version UNPINNED (Capacitor-6-era releases are ~1.8–1.13). No known exploitable CVE relevant to use here: it operates only on the app's own local SQLite DB, offline, with no attacker-controlled SQL ingress. CLEAN (version-unpinned caveat only).

Confidence: HIGH on manifest findings (read merged+packaged debug manifests + source directly). HIGH on pdf.js unreachability (traced the single getDocument call site to its blob source). MEDIUM on "sql.js clean" only because the version could not be pinned from the bundled artifact.

## [P1] sec-apk-1 — Distributed APK is a debug build — android:debuggable="true" ships to the owner's device
- **Module/area:** AndroidManifest / Gradle build variant | **Confidence:** high
- **Location:** android/app/build/intermediates/merged_manifests/debug/AndroidManifest.xml:27 (debuggable injected); only debug variant exists — no release manifest under packaged_manifests/
- **Defect:** The only build variant ever produced is the debug variant (only android/app/build/intermediates/{merged,packaged}_manifests/debug/ exist; no release/ dir). The debug build injects android:debuggable="true" into the application element, and the seeded distribution APK (SaagarCC-DemoData-V6-Wave3.apk per memory) is this debug artifact. A debuggable APK lets anyone with USB/adb access run `run-as com.saagartraders.bcc` and read the app's entire private data dir — including the primary SQLite business DB (sales, udhaar/credit ledger, payroll, GST figures) and the daily auto-backup — without root. It also allows attaching a JS/Java debugger to the live WebView.
- **Impact:** On a lost, stolen, serviced, or briefly borrowed phone, all of the shop owner's financial and customer data is trivially extractable via adb with no root and no PIN bypass. Debuggable production builds are a well-known OWASP MASVS failure (RESILIENCE).
- **Fix hint:** Ship a RELEASE build, not debug. Build via the existing `npm run build:release` (cap sync + gradlew assembleRelease) and distribute that signed APK instead of assembleDebug output. Release builds do not inject debuggable. No source/manifest edit required — this is a build-process fix. Do NOT hand-add android:debuggable="false" to the source manifest as a substitute; use the release variant. Obeys all hard rules (build-only, no libs, offline).

## [P1] sec-apk-2 — android:allowBackup="true" permits adb-backup exfiltration of the offline SQLite business/financial data
- **Module/area:** AndroidManifest.xml | **Confidence:** high
- **Location:** android/app/src/main/AndroidManifest.xml:5 (android:allowBackup="true"); carried into merged/packaged manifest line 25
- **Defect:** The application declares android:allowBackup="true" (the AGP default). Combined with minSdkVersion 22, this means `adb backup -f out.ab com.saagartraders.bcc` can pull the app's private files — the sql.js-backed SQLite database and the daily auto-backup blobs stored in app-private storage — off the device onto any PC, for any build (debug or release), without root. For an app whose entire value is holding a retailer's confidential ledgers (cash, udhaar, payroll, GST), full-data backup export is a meaningful confidentiality weakness.
- **Impact:** Anyone with brief physical access and USB debugging (or a device where the owner enabled it) can exfiltrate the complete business dataset via a standard adb backup, defeating the 'offline = safe' assumption. No malware or root needed.
- **Fix hint:** Set android:allowBackup="false" on the <application> element in android/app/src/main/AndroidManifest.xml (single attribute flip; app has no cloud-backup requirement — backups are handled internally via the daily auto-backup file the user controls). This is a manifest attribute change only: no new library, no storage-core/sqlite-store/photo-store edits, offline posture preserved. If finer control is later wanted, add a data-extraction/backup rules XML, but the simple false is sufficient and lowest-risk.

## [P2] sec-apk-3 — INTERNET permission requested but the app is fully offline (unnecessary attack surface)
- **Module/area:** AndroidManifest.xml | **Confidence:** medium
- **Location:** android/app/src/main/AndroidManifest.xml:40 (<uses-permission android.permission.INTERNET/>)
- **Defect:** The manifest declares android.permission.INTERNET, but a grep of the entire www payload (index.html, saagar-report.js) shows no fetch/XMLHttpRequest/WebSocket to any remote host. The only outbound interactions are tel: and https://wa.me/ links, which are OS-handled external intents (they launch the dialer / WhatsApp / browser) and do NOT require the app process itself to hold INTERNET. Capacitor serves the bundled www over the local https://localhost WebViewAssetLoader scheme, which also does not need INTERNET. Keeping INTERNET granted means that if any bundled JS were ever compromised (or a future dependency added), it could silently exfiltrate the local DB over the network — a capability the app otherwise does not need.
- **Impact:** Contradicts the app's advertised offline-only security model and leaves an exfiltration channel available to any injected/compromised script. Low immediate risk (no current code uses it), but it is free attack surface on an app holding sensitive financial data.
- **Fix hint:** Remove the <uses-permission android:name="android.permission.INTERNET"/> line from android/app/src/main/AndroidManifest.xml and re-verify on-device that (a) the app UI loads (localhost asset loading is unaffected) and (b) tel:/wa.me share still launch external apps. If a regression appears (some Capacitor/WebView configurations want INTERNET for the localhost scheme on certain OEMs), restore it — hence P2 not P1. Manifest-only change, no libs, offline preserved.

## [P3] sec-apk-4 — FileProvider file_paths grants whole external-storage and cache roots ('path="."')
- **Module/area:** AndroidManifest FileProvider config | **Confidence:** medium
- **Location:** android/app/src/main/res/xml/file_paths.xml:3-4 (external-path name="my_images" path="." ; cache-path path=".")
- **Defect:** The FileProvider path config exposes the root of external-files storage and the cache dir (path=".") rather than a narrow subfolder. The provider itself is android:exported="false" and only hands out content:// URIs via explicit grantUriPermission during the share flow, so this is not directly world-readable. However, scoping the provider to the entire external/cache root is broader than needed: any transient file the app writes there becomes eligible for a share-grant, widening the surface if a share intent is ever mis-targeted.
- **Impact:** Low. Not remotely exploitable and gated by exported=false + per-URI grants. It is a defense-in-depth / least-privilege gap rather than an active breach.
- **Fix hint:** Narrow file_paths.xml to the specific subdirectory used for outbound report/PDF sharing (e.g. a dedicated <cache-path name="shared_reports" path="shared/"/>) instead of path=".". XML-only change, no code/libs/storage-core touched, offline preserved. Low priority — safe to defer.

## [P3] sec-apk-5 — Bundled pdf.js 3.11.174 is within the CVE-2024-4367 affected range but the vulnerable path is UNREACHABLE (informational)
- **Module/area:** Bundled library — pdf.js (www/pdf.min.js) | **Confidence:** high
- **Location:** www/pdf.min.js (apiVersion "3.11.174"); sole consumer saagar-report.js:1456-1458 getDocument({url}) fed by URL.createObjectURL(blob) at :1429
- **Defect:** CVE-2024-4367 lets a crafted PDF execute arbitrary JS via a malicious FontMatrix when pdf.js < 4.2.0 renders it with isEvalSupported (default true); 3.11.174 is in range. Reachability was traced: the only getDocument() call site is saagar-report.js line 1456, whose input is a blob URL created at line 1429, and every caller passes a blob the app itself just generated in-process with jsPDF (renderDoc(...).output('blob')). The app never ingests an external PDF — it is fully offline and the single <input type=file> (index.html:1425) accepts application/json,.json only. There is no code path by which an attacker-controlled PDF reaches pdf.js, so the CVE is not exploitable in this app.
- **Impact:** None in practice given current code. Risk would only materialize if a future change added an 'open/import external PDF' feature that routed untrusted bytes into pdfjsLib.getDocument. Recorded so that constraint is not silently lost.
- **Fix hint:** No action required now (do not add libraries or upgrade pdf.js as part of this read-only audit). Preserve the invariant: keep the file input JSON-only and never feed externally-sourced PDF bytes to pdfjsLib.getDocument. If an external-PDF viewer is ever added later, upgrade pdf.js to >= 4.2.0 or set isEvalSupported=false at that time. Informational finding.
