# sec-postmessage-url — security audit

**Target:** shell message bus + wa/tel
**Findings:** 3

**Coverage notes:** THREAT-MODEL BOTTOM LINE (weights every finding): This is a packaged, fully-offline Capacitor APK. (a) The INTERNET permission is stripped at build time (.github/workflows/build-apk.yml:48-49; BUILD_NOTES.md; index.html:11) so NO remote or foreign page/frame can ever load — there is no cross-origin context that could postMessage the shell. (b) The ONLY message sender is #moduleFrame, a srcdoc iframe with NO `sandbox` attribute (index.html:1634; comment at 5752 "Same-origin iframe (no sandbox)"). A non-sandboxed srcdoc iframe is SAME-ORIGIN (https://localhost), NOT opaque/null — the INJECTION_PIPELINE.md "opaque-origin" premise is factually wrong. Because the module already runs same-origin, it already has parent.document access; postMessage is therefore NOT the privilege boundary. All modules are first-party HTML baked into index.html at build (mod.html_b64) — there is no untrusted-content ingress. CONCLUSION: the missing origin/source check and the unsanitized ST_PRINT innerHTML are genuine defense-in-depth weaknesses, but they are NOT offline-exploitable — forging any ST_* requires an attacker who is ALREADY running same-origin script, at which point postMessage is redundant with direct DOM control. No P0/P1 real breach found on the message bus. wa.me/tel construction is clean (Customer 360 phone is digit-sanitized `replace(/\D/g,'').slice(-10)`, text encodeURIComponent'd, rel=noopener; the WA composer produces owner-editable plain text sent to the OS share sheet with manual recipient — no wa.me URL, no phone/text injection). Message SHAPE validation is present and reasonable (id/action/reportType guards; module id validated against registry in openModule; date via /^\d{4}-\d{2}-\d{2}$/). HARD RULES respected: all fix hints are additive (add an origin/source allowlist guard + a shape whitelist at the top of the handler), no new libs, offline-only, no storage-core/sqlite-store/photo-store edits. Only 3 hardening findings below; none change money figures or cause data loss under the real offline threat model.

## [P2] pm-01 — Shell postMessage handler validates neither event.origin nor event.source (no allowlist)
- **Module/area:** shell message bus | **Confidence:** high
- **Location:** saagar-control-centre/www/index.html:6479-6492
- **Defect:** window.addEventListener('message', ...) dispatches ST_BACK_HOME, ST_OPEN_MODULE, ST_PRINT, ST_REPORT, ST_REPORT_BATCH, ST_SHARE, ST_WA and ST_AUDIT purely on e.data.type, with NO check of e.origin or e.source. Any window that can obtain a handle to the shell window could post a forged ST_* event. In principle this lets a foreign context trigger navigation, open a print/preview host, kick off report generation, or write audit-log entries.
- **Evidence:** index.html:6479 `window.addEventListener('message', e => { if(!e || !e.data) return;` then a flat series of `if(e.data.type === 'ST_...')` with no e.origin/e.source reference anywhere in the handler. Sender frame confirmed non-sandboxed same-origin: iframe#moduleFrame declared at 1634 with no sandbox attr; grep for `sandbox` in index.html returns only the prose comment at 5752.
- **Impact:** Defense-in-depth gap only under the shipped threat model. The app is a packaged offline APK with the INTERNET permission removed (build-apk.yml:48-49), so no remote/foreign page can ever load, and the sole real sender (#moduleFrame) is a non-sandboxed srcdoc iframe that is ALREADY same-origin (index.html:1634, 5752) with full parent.document access — so forging ST_* buys an attacker nothing they don't already have. There is no offline path for untrusted script to reach this listener. Real exploitability: effectively nil in this build; the risk would only materialise if a future build re-adds INTERNET, loads any remote content, opens an attacker-controllable window, or sandboxes the module frame to a null origin. Worth hardening now because the handler is the shell's single cross-frame trust seam.
- **Fix hint:** Additive guard at the top of the listener (no libraries, no storage-core touch): (1) accept only messages whose e.source === document.getElementById('moduleFrame').contentWindow (the one legitimate sender); (2) additionally gate on e.origin being the app origin (location.origin, i.e. https://localhost) OR the empty-string/'null' that same-origin srcdoc posts — test on-device since srcdoc origin reporting varies; (3) whitelist e.data.type against the known ST_* set and early-return otherwise. This preserves every current flow (all legit posts come from that frame) while closing the seam if the environment ever changes.

## [P2] pm-02 — ST_PRINT renders posted HTML+CSS via innerHTML into a TOP-LEVEL host (no sanitisation)
- **Module/area:** shell message bus / print bridge | **Confidence:** high
- **Location:** saagar-control-centre/www/index.html:6519-6551 (stPrintBridge), dispatched at 6483
- **Defect:** stPrintBridge takes e.data.html and e.data.css straight from the posted message and injects them into #st-print-host via host.innerHTML = ... + (data.css?'<style>'+data.css+'</style>':'') + (data.html||'') + ... . This host lives in the TOP document (not the iframe), is shown fullscreen (html.st-preview-open), and its content is later rasterised to PDF and can be printed. The HTML/CSS are inserted with zero sanitisation, so a forged or malicious ST_PRINT can place arbitrary markup (and, via the injected <style>, arbitrary CSS) into the shell's own document.
- **Evidence:** index.html:6530-6543 `host.innerHTML = '<div class="sp-toolbar">' ... + (data.css ? '<style>'+data.css+'</style>' : '') + (data.html || '') + '</div></div>' ...` ; host is #st-print-host appended to document.body at 6523; shown fullscreen top-level via html.st-preview-open (CSS 727). Reached from the unguarded handler at 6483 `if(e.data.type === 'ST_PRINT') stPrintBridge(e.data);`.
- **Impact:** This is the sharpest item on the bus because it moves attacker-shaped content OUT of the sandbox-less-but-still-iframe module and INTO the top document, and inline event handlers / crafted CSS would execute/apply in the shell context. However, under the shipped offline threat model the only entity that can post ST_PRINT is a first-party bundled module already running same-origin (see pm-01 threat model) — such a module can already scribble on parent.document directly, so no privilege is actually gained. No offline breach; the concern is that IF the origin check (pm-01) is ever the only thing standing between a future untrusted sender and this sink, this is the sink that turns a forged message into top-document HTML/CSS injection. Note img/script-src can still trigger sub-resource loads, but INTERNET is stripped so they cannot exfiltrate.
- **Fix hint:** Primarily fixed by pm-01 (only accept ST_PRINT from the module frame + type whitelist). As additional additive hardening without new libs: keep the injected <style> but wrap the print HTML build so it cannot introduce active content — e.g. strip on-* attributes and <script> from data.html with a small regex/DOM-parse-then-serialise pass before assigning innerHTML, or build into a detached document and import only element nodes. Do NOT add a sanitiser library (offline/no-new-libs rule) — a minimal inline scrub is sufficient given the same-origin-only sender.

## [P3] pm-03 — ST_AUDIT writes attacker-controlled action/detail/before/after into the audit log
- **Module/area:** shell message bus / audit log | **Confidence:** high
- **Location:** saagar-control-centre/www/index.html:6488-6491 (dispatch) → auditLog 2098-2107
- **Defect:** On ST_AUDIT the shell calls auditLog(e.data.action, e.data.detail||{}, e.data.before, e.data.after) with all four values taken verbatim from the posted message. auditLog unshifts the entry and persists JSON.stringify(log.slice(0,500)) to AUDIT_LOG_KEY. A forged ST_AUDIT can therefore inject arbitrary log entries (fake actions/actors-by-implication, bogus before/after blobs) or, by spamming, churn the 500-entry ring to evict genuine history.
- **Evidence:** index.html:6488 `if(e.data.type === 'ST_AUDIT' && e.data.action){ auditLog(e.data.action, e.data.detail||{}, e.data.before ?? null, e.data.after ?? null);` ; auditLog persists at 2106 `safeSet(AUDIT_LOG_KEY, JSON.stringify(log.slice(0,500)))`.
- **Impact:** Integrity/pollution of the on-device audit trail only — no money figure changes, no crash, no data-file corruption (the log is a bounded additive localStorage array). Under the offline model the only sender is same-origin module code that could write AUDIT_LOG_KEY directly anyway, so no real escalation. Low blast radius; flagged for completeness because audit-log trustworthiness is a stated concern and this is the poisoning vector.
- **Fix hint:** Covered by pm-01's source/type guard (only the module frame may post ST_AUDIT). Optionally, additively cap detail/before/after sizes and coerce action to a known-prefix string before logging so a single forged/oversized post can't bloat or evict the ring. No storage-core changes needed — auditLog already slices to 500.
