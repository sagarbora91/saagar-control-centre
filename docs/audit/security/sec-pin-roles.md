# sec-pin-roles — security audit

**Target:** shell auth/roles
**Findings:** 7

**Coverage notes:** Threat model is offline single-device, no server: threats = staff-vs-owner on a shared shop device, casual snooping, tampered backup from another device. Rated against THAT model, not a web/cloud model. The gating is a genuine navigation gate (ensureModuleAccess at line 2173 -> openModule at 5878) and the UI adminOnly toggling is cosmetic-only, but the FUNCTIONAL bypasses below matter because the adversary is a staff member with physical hands-on the device, which is exactly the model. Core design: PIN stored at st_v2_admin_pin_hash as simpleHash(pin); simpleHash (line 2091) is a 32-bit FNV-1a-style non-crypto hash returning a 10-digit string; admin session persisted as plaintext 'true' in localStorage key st_v2_admin_mode (setAdmin line 2134, restored at boot line 6733); safeGet/safeSet (2063-2065) are thin wrappers over plain window.localStorage. No brute-force throttle/lockout exists anywhere. There is NO legacy 'Gold' role path in the shell — the only 'gm_role'/Gold reference is the expense module's own PHP-era key handled purely as a restore-validation passthrough (line 5211), not a shell auth path; the shell roles are the ACCESS_ROLES list (Store Manager default). Reported honestly: because the threat model explicitly excludes a remote attacker and the whole DB is by-design plaintext on the device, none of these is a true P0 "security breach" in context; the realistic ceiling is P1 (meaningful weakness a curious staffer can exploit) down to P3. HARD RULES respected: all fix hints are additive-localStorage / no-new-lib / offline-only and never touch storage-core.js / sqlite-store.js / photo-store.js. NOTE these are code-hardening hints for a READ-ONLY audit; nothing was edited.

## [P1] SEC-PIN-01 — Admin session flag is a plaintext localStorage boolean — staff can self-promote to owner without the PIN
- **Module/area:** shell auth (admin mode) | **Confidence:** high
- **Location:** www/index.html:2134 (setAdmin), 6733 (boot restore), 1938 (ADMIN_MODE_KEY)
- **Defect:** Admin/owner mode is gated only by the in-memory flag `isAdmin`, which is persisted verbatim as the string 'true' under localStorage key st_v2_admin_mode (setAdmin, line 2134) and re-read on every boot (line 6733: `isAdmin = safeGet(ADMIN_MODE_KEY)==='true'`). The PIN check in unlockAdmin (2149) is the ONLY thing that normally flips this flag, but nothing binds the persisted flag back to the PIN. Concrete bypass on a shared shop device: a staff member opens the app's WebView in a debuggable build / connected browser devtools / or any file-manager that can reach the app's localStorage, runs `localStorage.setItem('st_v2_admin_mode','true')` (or, in the app, evaluates `setAdmin(true)`), reloads, and is now owner — payroll, tax, backup, restore, wipe, role editor all unlocked, PIN never entered. `isAdmin===true` makes ensureModuleAccess (2174) and roleCanOpen (1991) return true unconditionally. This is the highest-leverage weakness: it defeats the PIN entirely without ever attacking the hash.
- **Impact:** On a shared owner/staff device a curious or malicious staffer gains full owner access (payroll salaries, tax figures, delete/restore/wipe of all data) by setting one localStorage string, with no PIN. Realistic on a debuggable APK or if the device WebView is inspectable. Does not require cracking the hash.
- **Fix hint:** Do not trust a standalone persisted admin-mode boolean. Additive-localStorage fix: on boot, only honor st_v2_admin_mode==='true' if a companion token derived from the current PIN hash also matches — e.g. store alongside it a value `simpleHash(pin_hash + 'admin-session-v1')` and recompute+compare from st_v2_admin_pin_hash at boot; if it doesn't match, force isAdmin=false. This ties the session flag to knowledge of the PIN without new libs. (Cannot make it truly tamper-proof in an offline WebView, but raises it well above a one-word edit.) Better still, do not persist admin mode across launches at all — default isAdmin=false every boot so a staffer can't leave it unlocked. Obeys hard rules; no storage-core edits.

## [P1] SEC-PIN-02 — PIN hash is a fast 32-bit non-cryptographic hash with no salt and no attempt throttling — trivially brute-forced offline
- **Module/area:** shell auth (PIN) | **Confidence:** high
- **Location:** www/index.html:2091 (simpleHash), 2142 (store), 2148-2149 (verify)
- **Defect:** The PIN is stored as simpleHash(pin) (line 2142), where simpleHash (2091) is an unsalted FNV-1a-style function collapsing input to a 32-bit value rendered as a <=10-digit decimal string. It is not a KDF, not salted, and reversible-by-search: a 4-digit numeric PIN (the enforced minimum is only length>=4, and shop staff overwhelmingly pick 4-6 digit PINs) has 10k candidates; simpleHash over all of them takes microseconds. Given read access to st_v2_admin_pin_hash (same device, same localStorage as SEC-PIN-01), an attacker recovers the actual PIN by brute force, then enters it normally so no tampering is visible. Additionally unlockAdmin (2148) has NO attempt counter, delay, or lockout (confirmed: no throttle/lockout code exists), so even blind on-device guessing of a 4-digit PIN is feasible by hand and instant by script. The 32-bit space also admits collisions, but brute-forcing the small PIN space is the practical attack.
- **Impact:** Anyone who can read the stored hash (trivial on this device — plaintext localStorage) recovers the owner PIN, defeating payroll/tax protection and any future PIN-gated action. No lockout means even naive repeated guessing is unpunished.
- **Fix hint:** Within hard rules (no new libs / offline): (a) strengthen the stored hash to a slow, salted, many-round construction built only from simpleHash — e.g. generate a random per-device salt (crypto.getRandomValues), store it, and store simpleHash iterated N thousand times over salt+pin; verify the same way. This kills precomputation and slows brute force. (b) Add an attempt counter in localStorage: after e.g. 5 wrong PINs impose an escalating delay / disable unlock for a cooldown window, so hand-guessing a 4-digit PIN is not instant. (c) Consider requiring 6+ digits. All additive-localStorage, no storage-core touch. Note: on an offline device a determined attacker with the hash can still brute force eventually — the goal here is raising cost above 'microseconds and no lockout'.

## [P1] SEC-PIN-03 — Protected-module data is only navigation-gated, not withheld — payroll/tax figures are readable from plaintext localStorage regardless of PIN or role
- **Module/area:** shell auth (module gating) | **Confidence:** high
- **Location:** www/index.html:2173 (ensureModuleAccess), 2063 (safeGet), 1928/1930 (payroll/tax keys)
- **Defect:** ensureModuleAccess (2173) and the tile lock icon (3405) only decide whether openModule (5878) will NAVIGATE to the module iframe. The sensitive data itself lives in ordinary localStorage keys (payroll under 'payroll_suite_v1_2026', tax under 'taxcal_v2' — see the module key registry at 1928/1930) written/read via plain safeGet/safeSet (2063-2065). The PIN gate never encrypts or hides those keys. Concrete bypass on the shared device: without ever unlocking admin, a staffer with devtools/file access reads `localStorage.getItem('payroll_suite_v1_2026')` and gets every salary; same for tax. So the 'Admin PIN required for this module' toast (2178) protects only the pretty in-app view — the owner may believe payroll salaries are hidden from staff, but they are hidden only visually. This matches the audit concern 'whether hidden data is only visually hidden' — it is.
- **Impact:** Owner's expectation that PIN-protecting Payroll/Tax keeps salary and tax figures away from staff is only cosmetically true. Any staffer who can reach the device's localStorage sees the raw numbers with no PIN and no role. Wrong mental model about who can see the money figures.
- **Fix hint:** True confidentiality of module data on an offline device requires at-rest encryption of those blobs keyed by the PIN — which is a large change and the data engine (storage-core.js / sqlite-store.js) is off-limits per hard rules, so DO NOT attempt to encrypt via those. The honest, in-scope fix is expectation-setting: reword the protection copy (e.g. Settings 'Require admin PIN…' description near line 1493 and the toast at 2178) to state it restricts the in-app view only and is not encryption, so the owner does not overtrust it. If encryption is later desired it must be scoped as its own project touching the storage layer deliberately, not bolted on here.

## [P1] SEC-PIN-04 — Restore accepts an attacker-supplied admin PIN hash and admin-mode flag from a backup file — tampered migration file can preset owner access or swap the PIN
- **Module/area:** shell auth (backup/restore) | **Confidence:** high
- **Location:** www/index.html:5206 (validateRestoreKeyValue control-keys), 2070 (appControlKeys export list)
- **Defect:** The audit's own threat model includes 'tampered backup/migration file from another device'. appControlKeys (2070) exports/imports ADMIN_PIN_KEY and ADMIN_MODE_KEY, and validateRestoreKeyValue (5206) explicitly returns {ok:true} for ADMIN_PIN_KEY, ADMIN_MODE_KEY and PROTECTED_MODULES_KEY with no content check. So a backup/migration JSON crafted on another device can carry st_v2_admin_mode='true' (device boots already-owner, SEC-PIN-01) and/or st_v2_admin_pin_hash set to simpleHash of a PIN the attacker knows, and/or st_v2_protect_admin_modules='false' (disables payroll/tax gating outright). Concrete attack: attacker hands the shop a 'migration file' (a supported flow per the memory notes); after restore, the attacker's PIN is the device PIN, or protection is off, or admin is pre-unlocked — the legitimate owner is unaware their PIN was replaced. Because the restore validator waves these control keys through, the tampered file needs no special format.
- **Impact:** A malicious or swapped migration/backup file silently grants the attacker owner access on the target device (known PIN, or pre-unlocked, or protection disabled), defeating the whole PIN/role scheme after a routine restore. Directly in the stated threat model (tampered file from another device).
- **Fix hint:** Additive, no-storage-core: exclude the auth control keys (ADMIN_PIN_KEY, ADMIN_MODE_KEY, PROTECTED_MODULES_KEY) from RESTORE — restore should never import someone else's PIN hash or unlock state. Keep them exportable for the owner's own device migration only behind a confirm, but on import either (a) skip them entirely and preserve the current device's PIN, or (b) require re-entering the CURRENT device PIN before allowing these three keys to be overwritten. At minimum, after any restore force isAdmin=false and require a fresh PIN unlock. Change is in the restore/validate path (around 5206) and setAdmin call sites, not the storage engine.

## [P2] SEC-PIN-05 — First-run 'set a PIN' is opportunistic, so a fresh/never-configured device grants owner access on first unlock tap with a self-chosen PIN
- **Module/area:** shell auth (PIN bootstrap) | **Confidence:** medium
- **Location:** www/index.html:2146-2147 (unlockAdmin no-pin branch), 2135 (promptNewPin)
- **Defect:** unlockAdmin (2146) treats 'no PIN configured yet' as: prompt the caller to CREATE a PIN then immediately grant admin (line 2147: `if(!hasAdminPin()){ if(!promptNewPin()) return; setAdmin(true); return; }`). On a device where the owner never set a PIN (default state — hasAdminPin false), the FIRST person to tap 'Unlock admin' — which may be a staffer, not the owner — sets the PIN to a value THEY choose and becomes owner. There is no distinction between 'owner initializing' and 'staffer squatting'. Combined with the shared-device model this is a real land-grab: whoever gets there first owns the device auth. Lower severity than the above only because it requires the owner to have never configured a PIN.
- **Impact:** On an unconfigured shared device the first (possibly untrusted) person to open admin claims the PIN and owner role, locking the actual owner into re-taking it. Weakens the trust model on fresh installs.
- **Fix hint:** Encourage/force PIN setup as part of first-run owner onboarding (a one-time setup step the owner completes before staff use), rather than lazily on first unlock tap. Additive: show a clear first-run banner prompting the owner to set the admin PIN immediately, and/or record in localStorage that setup was completed by the owner. No storage-core changes.

## [P2] SEC-PIN-06 — Role switch is unauthenticated — any staffer can select 'Store Manager' (all-modules) from the role picker with no PIN
- **Module/area:** shell auth (roles) | **Confidence:** high
- **Location:** www/index.html:1989-1991 (currentRole/setCurrentRole/roleCanOpen), 5634 (config role select)
- **Defect:** The per-device role lives in localStorage key saagar_current_role_v1 and is changed by setCurrentRole (1990), which is wired to the role <select> in Settings (populated at 5634 / 2132). Selecting a role requires NO PIN and no admin — currentRole defaults to 'Store Manager', which defaultRoleAccess (1979) grants ALL modules. So a Cashier (whose role only allows 'expense') can simply open the role dropdown and switch the device to 'Store Manager', instantly granting themselves every non-PIN-protected module (stock, service, qms, dsr, grooming, cro_audit, leave, planning). Only payroll/tax remain behind the PIN gate; everything else the role system 'restricts' is one dropdown selection away. The role matrix is therefore advisory, not enforced against a hands-on staffer. (Note: the role editor card is adminOnly, but the current-role SELECT that switches roles is reachable in staff view per line 2132/5634.)
- **Impact:** Role-based module restriction is defeated by picking a different role from the visible dropdown; a limited-role staffer self-escalates to all non-PIN modules with zero authentication. Owner's per-role lockdown is not real for a curious staffer.
- **Fix hint:** Gate role SWITCHING behind admin/PIN: require unlockAdmin() (or a confirm that the owner is present) before setCurrentRole can move to a higher-privilege role, or make the current-role selector adminOnly like the role-access editor already is. Additive change in setCurrentRole (1990) and the select's onchange wiring; no storage-core touch. Also consider that a device-wide 'current role' is inherently weak when staff share one device — document that roles are a convenience filter, not a security boundary.

## [P2] SEC-PIN-07 — changeAdminPin does not re-verify when already unlocked, so a left-unlocked session lets a passerby silently reset the owner PIN
- **Module/area:** shell auth (PIN change) | **Confidence:** medium
- **Location:** www/index.html:2156-2163 (changeAdminPin)
- **Defect:** changeAdminPin (2156) only asks for the CURRENT PIN inside the `if(!isAdmin)` unlock path; when isAdmin is already true it skips straight past the old-PIN check to promptNewPin (2163). Because admin mode persists across launches (SEC-PIN-01) and there is no auto-lock/timeout, the common shop scenario is: owner unlocks admin, walks away, leaves the app; a staffer opens Settings -> Change PIN and, since isAdmin is still true, is NOT asked for the old PIN and can set a new one they know — hijacking the owner's admin. Line 2159's `if(old){...}` guard is unreachable while already-admin because that branch is inside the earlier no-isAdmin block flow only when unlock was needed; when already admin it drops through to promptNewPin without ever comparing `old`.
- **Impact:** An unattended unlocked device lets anyone reset the owner PIN without knowing it, permanently taking over admin. Aggravated by admin mode persisting and never auto-locking.
- **Fix hint:** Always require the CURRENT PIN before setting a new one, even when isAdmin is already true — move the old-PIN verification (2159-2162) so it runs unconditionally when an admin PIN exists. Also add an auto-lock: clear isAdmin after N minutes idle or on app background so a walked-away session cannot be abused. Both additive; no storage-core changes.
