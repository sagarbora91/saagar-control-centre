## [P1] SEC-DATA-01 — Restore rollback snapshot write is unchecked — quota failure leaves a destructive overwrite with NO undo
- **Module/area:** restore | **Confidence:** high | **Combo:** near-full localStorage + Restore from JSON
- **Location:** www/index.html:5279-5291 (restoreValidatedBackup); safeSet swallows quota at :2064
- **Defect:** restoreValidatedBackup() takes the pre-restore rollback by building a full JSON of the current values of every key about to be overwritten and calling safeSet(rollbackKey, JSON.stringify(rollback)) at line 5285. Its return value is DISCARDED. safeSet (line 2064) catches QuotaExceededError, shows a toast, and returns false WITHOUT throwing. localStorage is a fixed ~5-10MB budget shared across all app keys; when the device is already near full (exactly the scenario a large restore aggravates) the rollback write silently fails. Execution then falls straight through to the bulk overwrite loop (line 5290) which replaces the live keys anyway. The advertised 'A rollback snapshot will be saved before any data is replaced' (line 5258) is therefore a false promise on a full device.
- **Evidence:** 5285: safeSet(rollbackKey, JSON.stringify(rollback));  — return ignored, immediately followed by 5290-5291 overwrite. safeSet at 2064 returns false on QuotaExceededError instead of throwing.
- **Impact:** On a near-full device, a restore that the user believes is undoable irrevocably overwrites live business data (stock, expense ledger, payroll, udhaar) with the imported values, and the rollback the UI promised does not exist. If the imported file is wrong/stale, the pre-restore data is unrecoverable from within the app. Silent partial/total loss.
- **Fix hint:** Additive-only: capture the boolean return of safeSet(rollbackKey,...) at line 5285; if false, ABORT the restore before the write loop with an alert ('Rollback snapshot could not be saved — free space or export a backup first; nothing was changed'). Optionally also verify rollback readback (safeGet(rollbackKey)!==null) like the factory-reset path already does. No new libs, additive localStorage only.

## [P1] SEC-DATA-02 — saagar_bridge_config (cross-module integration rules) is not whitelisted — silently dropped by backup AND restore, but wiped by factory reset (net data loss beyond the two known keys)
- **Module/area:** backup/restore/reset completeness | **Confidence:** high | **Combo:** configure integration rules → factory reset or restore-on-new-device
- **Location:** www/index.html:2765 (writer), 1923-1935 STORAGE_RULES, 2070 appControlKeys, 2072 isWhitelistedAppKey, 5362 factory-reset APP_RE
- **Defect:** saveBridgeConfig() persists 'saagar_bridge_config' (line 2765) holding the live cross-module automation rules: failPct, voucherThreshold, leaveGates — user-editable in Settings. This key is NOT in appControlKeys() (line 2070) and NOT matched by any STORAGE_RULES exact/prefix (line 1923-1935: prefixes are saagar_stock_ / saagar_grooming_ / saagar_dsr_, none match saagar_bridge_config). Therefore isWhitelistedAppKey('saagar_bridge_config') === false. Consequences: (a) manual backup (backupPayload→appStorage→isWhitelistedAppKey filter) EXCLUDES it; (b) restore (validateRestoreData line 5225) pushes it to rejected[] and never writes it; (c) BUT factory-reset APP_RE /^saagar_.../ (line 5362) DELETES it. The pre-reset safety backup folds it in (line 5393 loops the APP_RE keys), yet restoring that safety file silently drops it again at the whitelist gate — so the round trip loses it either way. This is a THIRD whitelist gap distinct from the two already-known bugs (saagar_invoice_seq_v1 / saagar_wsf_settings_v1 are IN STORAGE_RULES.service and fail on TYPE validation, a different defect).
- **Evidence:** 2765 safeSet('saagar_bridge_config',...); 2070 appControlKeys list has no bridge_config; 1923-1935 no STORAGE_RULES match; 5362 APP_RE matches saagar_ → wiped; 5225 non-whitelisted → rejected on restore.
- **Impact:** After a restore-to-new-phone or a factory-reset+restore, the owner's configured integration thresholds (voucher approval threshold, service-fail %, leave gating) silently revert to code defaults (2000 / 60 / on) — a quiet business-logic regression the user is unlikely to notice until an approval or gate behaves unexpectedly. Backup completeness is also violated: the key the auto-backup DOES capture (full snapshot) can never be restored.
- **Fix hint:** Additive: add 'saagar_bridge_config' to appControlKeys() (line 2070) so it is whitelisted for export AND restore, and add a matching validateRestoreKeyValue branch (owner==='control' object check). This makes backup/restore symmetric with the auto-backup full snapshot. Additive localStorage/whitelist only, no libs.

## [P1] SEC-DATA-03 — Restore is additive-merge with no pre-clear — a mid-import failure or a partial backup leaves inconsistent cross-module state
- **Module/area:** restore atomicity | **Confidence:** medium | **Combo:** restore a stale/partial or oversized backup
- **Location:** www/index.html:5279-5291 (restoreValidatedBackup), 5222-5233 (validateRestoreData)
- **Defect:** restoreValidatedBackup() writes only the keys present-and-valid in the imported file (Object.keys(review.valid)) and NEVER clears keys that exist on-device but are absent from the backup. It is a key-by-key overwrite inside SaagarStore.bulk() (line 5291). Two integrity consequences: (1) NON-ATOMIC vs. the live DB — validation runs before the write, but if a mid-loop safeSet throws for one key (e.g. a single oversized value or a transient quota edge) subsequent keys silently do not get written (written++ only increments on success, no rollback is triggered), leaving a half-restored mix of old and new keys across modules. (2) MERGE-not-replace — restoring an OLDER or module-partial backup onto a device that has newer data for other modules yields a Frankenstein state: e.g. restored stock/service rows keyed to employees or customers that the (older) EMP_MASTER/CUST_MASTER in the same file references, mixed with day-keys the backup never touched. Referential consistency across modules (employee IDs, store keys, udhaar↔customer) is not enforced on import.
- **Evidence:** 5290: keys.forEach(k=>{ if(safeSet(k,review.valid[k])) written++; }); — no per-key failure handling, no on-device key removal, no whole-restore transaction/rollback trigger.
- **Impact:** Inconsistent cross-module data after a restore that partially fails or is applied from a stale/partial file: dangling references (rows pointing at employee/customer IDs that differ), stock/DSR/grooming day-keys from a different era coexisting with restored masters. No transaction wraps the whole restore, so there is no all-or-nothing guarantee; the rollback key (see SEC-DATA-01) is the only recovery and it can silently be absent.
- **Fix hint:** Additive: after the bulk write, compare written vs keys.length; if written<keys.length, surface a hard warning and offer the rollback key immediately rather than reloading into a mixed state. Consider gating restore on payload.version/apkBuild compatibility (already present in payload) and warning when the file predates on-device data. No pre-clear change needed to satisfy the additive-only rule.

## [P2] SEC-DATA-04 — No size/shape guard on imported backup — a huge or deeply nested JSON can OOM/freeze the WebView during parse or double the footprint via the rollback
- **Module/area:** restore robustness | **Confidence:** medium | **Combo:** import a multi-MB migration/photo backup on a low-RAM device
- **Location:** www/index.html:5234-5277 (handleRestoreFile), 5279-5285 (rollback build)
- **Defect:** handleRestoreFile() does reader.readAsText then JSON.parse(reader.result) (line 5240) with no size cap and no streaming. A hostile or accidentally-huge file (the migration export itself can be MBs with embedded photos/evidence as base64) is fully materialized as a string, parsed to an object, re-validated (each value re-stringified at line 5226 for non-string values), then on apply a SECOND full copy is built for the rollback (line 5283-5284) and written back into the same localStorage budget. Peak memory is several multiples of the file size, and the whole thing runs on the main thread (no worker), freezing the UI. JSON.parse is in try/catch so it cannot crash-loop, and WAL replay (storage-core.js:146-159) wraps every op in try/catch and never JSON-parses stored values — so a bad restored value cannot throw on every boot. The realistic worst case is a hang / quota-exceeded toast, not an unrecoverable crash-loop.
- **Evidence:** 5240 JSON.parse(reader.result) unbounded; 5283-5284 second full copy for rollback into same LS budget; storage-core.js:151-158 replay try/catch per op, values kept as strings (no boot crash-loop).
- **Impact:** UI freeze or an out-of-memory reload while importing an oversized file; combined with SEC-DATA-01 the quota pressure from the rollback copy is what tips a large-but-legitimate restore into the silent-no-rollback failure. Bounded (no persistent corruption) because parse and replay are both guarded.
- **Fix hint:** Additive: reject files above a sane byte threshold (e.g. warn >8MB) before JSON.parse, and cap/skip the rollback copy for very large payloads with an explicit 'no rollback for this size — export current data first' prompt. No new libs.

## [P3] SEC-DATA-05 — UI/session keys (saagar_ui_mode, ui_hide_amounts, ui_day_closed, saagar_acting_as, saagar_selected_date) are wiped by factory reset but excluded from backup/restore
- **Module/area:** backup completeness | **Confidence:** high | **Combo:** factory reset or restore, then observe UI defaults
- **Location:** www/index.html:6681/6700 (saagar_ui_mode), 3012 (ui_hide_amounts), 2920/2977 (ui_day_closed), 2861/2863 (saagar_acting_as), 2022/2030 (saagar_selected_date)
- **Defect:** These five live keys match the factory-reset APP_RE (saagar_ / ui_ via... actually ui_day_closed and ui_hide_amounts do NOT match APP_RE, but saagar_ui_mode, saagar_acting_as and saagar_selected_date DO) so the saagar_-prefixed ones are wiped on factory reset, while none are whitelisted, so none are exported or restored. Unlike SEC-DATA-02 these are non-durable UI/session state (view date is clamped to today; ui_day_closed is an EOD lock; acting_as is a transient role) so loss is cosmetic and self-heals on next use — noting only for completeness against STORAGE_RULES.
- **Evidence:** 2861 ACTING_AS_KEY='saagar_acting_as'; 2920 EOD_CLOSED_KEY='ui_day_closed'; 3012 'ui_hide_amounts'; 6681 UI_MODE_KEY='saagar_ui_mode'; 2022 SELECTED_DATE_KEY='saagar_selected_date'; none in appControlKeys (2070) or STORAGE_RULES (1923).
- **Impact:** Trivial: after a restore or reset the device re-defaults UI mode, un-hides amounts, clears the EOD lock and acting-as role. No business data lost; state reconstructs on normal use. Flagged so the whitelist gap is documented, not because it needs fixing.
- **Fix hint:** Optional/additive: if EOD-lock or acting-as continuity matters, add ui_day_closed and saagar_acting_as to appControlKeys(); otherwise document as intentionally-ephemeral. No change strictly required.
