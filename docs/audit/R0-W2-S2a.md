## Honest threat verdict (contract B1 — for the owner, an advocate)
Hardware Keystore key-wrapping means: a copy of the DATA dir taken **off the device** (adb pull, forensic image,
misdirected share) yields `SBCC1` ciphertext + an `SKW1` wrapped-DEK **both useless off-device** — the KEK never leaves
the TEE/StrongBox. It does **NOT** protect: a rooted/live-instrumented device running as the app (it unwraps headlessly,
so it can be driven); key fragility (uninstall / factory reset / **lock-screen credential change** kills the KEK →
ciphertext permanently unrecoverable, recover from plaintext backups or nothing); hardware variance (StrongBox is rare,
API-22 has no AES Keystore → plugin reports the true tier, never claims hardware when it's software); and the manual
plaintext exports (deliberate, gated). **Do not claim "encrypted at rest" to a third party until the writer ships +
the DT matrix passes.**

## INERTNESS (why S2a is safe with the flag off)
`encryptForPersist` has **zero live callers** (persist still `bytesToB64(db.export())` synchronously — E3 unwired), and
the reader `getDEK(false)` is reached only for an actual `SBCC1` envelope that cannot exist yet. So a production
auto-boot **mints no KEK and writes no `bcc.dek`** — identical safety to S1. Verified by grep + code trace.
