## [P0] dsr-bug-01 — Bridge-created DSR record crashes the whole staff panel (missing cleaning.cp1/cp2)
- **Module/area:** dsr | **Confidence:** high
- **Location:** dsr.html normalizeRecord() lines 1427-1444; crash sites updateProgress() line 1739 (rec.cleaning.cp1.done) and renderDayStart() line 1796; feeder integration-bridge.js ensureDsr() line 194 creates {cleaning:{}, marketing:{}}
- **Defect:** The bridge's ensureDsr() (integration-bridge.js:194) creates a DSR record with cleaning:{} and marketing:{} (no cp1/cp2 objects) and persists it via S(ed.k,ed.r). This happens whenever a CRO has QMS customers ALLOCATED (consumeQmsAllocatedToDsr) or CLOSED (consumeQmsToDsr) before that CRO has ever opened DSR that day. When the CRO logs in, getRecord() loads that key and runs normalizeRecord(), which normalizes opening/closing/tasks/nonpurch/visitors but NEVER ensures rec.cleaning.cp1/cp2 (or marketing/inout/sales). enterStaffPanel() immediately calls updateProgress() -> line 1739 `rec.cleaning.cp1.done && rec.cleaning.cp2.done` -> rec.cleaning.cp1 is undefined -> TypeError 'Cannot read properties of undefined'. renderDayStart() (default landing tab) hits the same at line 1796. Repro: any CRO with a QMS-allocated walk-in opens DSR for that day -> panel throws on entry, unusable.
- **Evidence:** normalizeRecord (1427-1444) omits cleaning/marketing/inout/sales; updateProgress line 1739 `rec.cleaning.cp1.done && rec.cleaning.cp2.done`; bridge ensureDsr line 194 `...cleaning:{},marketing:{}...` then S(ed.k,ed.r) at 219/250
- **Impact:** Staff DSR panel is completely unusable (uncaught TypeError on login) for exactly the busiest CROs — those who got QMS walk-ins. Core daily flow (opening stock, sales, closing, submit) is fully blocked. This is the app's historic undefined-deref crash class.
- **Fix hint:** In normalizeRecord(), additively ensure the shape renderers assume: `rec.cleaning=rec.cleaning||{}; ['cp1','cp2'].forEach(k=>{rec.cleaning[k]=rec.cleaning[k]||{done:false,photo:null,time:null};}); rec.marketing=rec.marketing||{calls:0,whatsapp:0,door:0,instore:0}; if(!Array.isArray(rec.inout))rec.inout=[]; if(!Array.isArray(rec.sales))rec.sales=[];`. Read-only/additive, no libraries, do NOT touch the bridge.

## [P0] dsr-bug-02 — Last-writer-wins race between bridge whole-record writes and DSR in-memory cache → data loss
- **Module/area:** dsr | **Confidence:** high
- **Location:** dsr.html _recCache/getRecord lines 1527-1558, scheduleRecSave/_writeRecNow lines 1529-1575; bridge writer integration-bridge.js S(ed.k,ed.r) line 219 and S(ed.k,r) line 250 (both on the ~60s tick)
- **Defect:** DSR keeps the live editable record in memory (_recCache) and coalesces writes with a 300ms debounce (scheduleRecSave -> _writeRecNow does setItem(JSON.stringify(rec))). The bridge, on its ~60s tick, reads the SAME key fresh (ensureDsr -> L(k,null)), appends a QMS sale/nonpurch/visitor, and writes the whole record back. Two clobber directions: (a) bridge reads storage lacking the staff's in-flight un-flushed edits, appends, writes — then 300ms later the DSR debounce fires _writeRecNow with the CACHED record (lacking the bridge's row) and overwrites, losing the QMS sale/visitor; (b) staff re-saves the cached copy that never saw the bridge row. Both are whole-blob overwrites with no merge/version check. Repro: CRO typing closing stock (debounced, un-flushed) when a QMS SALE_CLOSED fires; the QMS auto-sale row silently vanishes after the next keystroke's debounce flush.
- **Evidence:** getRecord returns cached rec without re-read (1546); _writeRecNow blind setItem (1533); scheduleRecSave 300ms debounce (1570-1575); bridge whole-record write (integration-bridge.js:219,250)
- **Impact:** Silent data loss of QMS-linked sales/visitors OR of staff edits depending on timing. Auto-filled QMS money rows can disappear from a CRO's day with no error. Non-deterministic, hard to reproduce.
- **Fix hint:** On the DSR side, re-read + merge instead of blind overwrite: in _writeRecNow, before setItem, read the current stored record and merge in bridge-owned rows (sales/nonpurch/visitors whose source starts with 'qms') keyed by sourceRef that are absent from the in-memory rec, then write. Or union bridge-added qms* rows on every getRecord/flush. Additive localStorage only; cannot edit the bridge.

## [P1] dsr-bug-03 — DSR panel never re-reads storage after caching → bridge-injected QMS visitors/sales invisible all session
- **Module/area:** dsr | **Confidence:** high
- **Location:** dsr.html getRecord() lines 1544-1558 (cache-hit early return line 1546); no storage listener
- **Defect:** getRecord() returns _recCache.rec whenever the key matches; the cache is invalidated only on date/staff change or logout. There is NO storage-event listener and no periodic re-hydrate. When the bridge injects a new QMS_ALLOCATED visitor (consumeQmsAllocatedToDsr) or a SALE_CLOSED sale into the currently-open day's record, the DSR Visitors/Sales tabs keep showing the stale cached array until the CRO switches date or reloads. A CRO watching the Visitors tab for allocated walk-ins never sees them appear.
- **Evidence:** getRecord line 1546 `if (_recCache.key === k && _recCache.rec) return _recCache.rec;` — no re-read path; cache invalidated only in logout()/applyViewDate
- **Impact:** Real-time QMS→DSR walk-in allocation (the entire purpose of the Visitors tab) does not surface live; the CRO can miss customers allocated during the shift. Combined with bug-02 those invisible rows are also clobbered on next save.
- **Fix hint:** Add a window 'storage' listener or a ~15-30s re-hydrate that, when the current key's stored record has qms* rows (by sourceRef) absent from _recCache.rec, merges them and re-renders the active tab. Merge (not replace) to preserve in-flight edits. Additive.

## [P1] dsr-bug-04 — calcTimeOut mixes Unix epoch seconds with seconds-since-midnight → garbage 'time out' while currently out
- **Module/area:** dsr | **Confidence:** high
- **Location:** dsr.html calcTimeOut() line 1893 `total += Date.now()/1000 - outTime;` with parseHMS() lines 1896-1899; shown by renderInOut line 1863
- **Defect:** parseHMS() returns seconds-since-midnight (0..86400). The running-total branch (line 1893) adds Date.now()/1000 (Unix epoch seconds, ~1.75e9) minus outTime (seconds-since-midnight). Result is ~1.75 billion seconds; fmtDur() renders it as e.g. '486000h 0m'. Fires whenever the last In/Out event is 'out' with no matching 'in' (staff currently out), because renderInOut shows 'Time out today: '+fmtDur(dur) when dur>0.
- **Evidence:** line 1893 `if (outTime) total += Date.now()/1000 - outTime;`; parseHMS line 1898 returns `h*3600+m*60+(s||0)`
- **Impact:** The In/Out card shows an absurd multi-hundred-thousand-hour 'Time out today' value the moment a staff member marks out. Non-catastrophic (informational; self-corrects once they mark back in and both timestamps are seconds-since-midnight) but visibly broken.
- **Fix hint:** Use current seconds-since-midnight to match parseHMS: `const n=new Date(); const nowSec=n.getHours()*3600+n.getMinutes()*60+n.getSeconds(); if(outTime) total += nowSec - outTime;`. Pure arithmetic, no libraries.

## [P1] dsr-bug-05 — Dashboard / range queries JSON.parse photo-laden records → large-blob parse burst (ANR risk)
- **Module/area:** dsr | **Confidence:** medium
- **Location:** dsr.html getAllInRange() lines 1585-1597, getAllForDate() 1576-1584, renderDashboard() reads getAllInRange (line 2681), handlePhoto stores full data URLs lines 2297-2312
- **Defect:** handlePhoto() stores each cleaning photo as a base64 data URL directly in the record (up to 1MB file -> ~1.33MB base64 per checkpoint, ~2.7MB for both). getAllInRange() JSON.parse()s EVERY DSR record in the 30-day window — including both photo blobs per record — for the dashboard and CSV export, holding every parsed record (with megabytes of base64) in the recs array at once. For several CROs over 30 days this is tens-to-hundreds of MB parsed synchronously on the srcdoc main thread. Also _writeRecNow re-stringifies both photos on every debounced save once photos are attached (e.g. while typing closing stock after cleaning).
- **Evidence:** getAllInRange line 1593 `recs.push(JSON.parse(localStorage.getItem(k)))` over all in-range keys; handlePhoto stores e.target.result (data URL) line 2305; dashboard recs held together 2681-2696
- **Impact:** Main-thread stall / ANR when the SM opens Dashboard or exports 30-day CSV on a device with real seeded photo data — the whole-blob JSON.parse crash class the app has hit before. Also per-keystroke jank after photos attached.
- **Fix hint:** For aggregation, avoid parsing full photo blobs: add a 'lite' path in getAllInRange/getAllForDate that JSON.parse then immediately deletes cleaning.cp*.photo before the next iteration, or store photos under a separate key so the main record stays small. Keep photo rendering only in the single-record audit view. photo-store.js must not be touched; additive only.

## [P1] dsr-bug-06 — DSR_SUBMITTED score always null — bridge reads audit.score, DSR writes audit.total
- **Module/area:** dsr | **Confidence:** high
- **Location:** dsr.html submitAudit() line 2665 writes audit={approved,total,...scores,...} (no `score`); bridge integration-bridge.js line 145 reads score:(r.audit&&r.audit.score)||null
- **Defect:** The SM audit stores the numeric result as r.audit.total (dsr.html:2665). The bridge's DSR_SUBMITTED emitter reads r.audit.score (integration-bridge.js:145), which never exists, so the emitted payload score is always null. Downstream the payroll feed (consumeDsrToPayroll: `if(p.score!=null){o.scoreSum+=...}`) and the CRO-audit feed never receive the DSR audit score.
- **Evidence:** dsr.html:2665 `st.auditRec.audit = { approved, total, ...scores, remarks:..., auditTime:nowTime() }`; integration-bridge.js:145 `score:(r.audit&&r.audit.score)||null`
- **Impact:** SM audit scores never propagate to payroll's avg-score bucket or cross-module dashboards consuming DSR_SUBMITTED.score — those columns read blank/zero even though the SM scored the day. Wrong/blank performance figures shown to the owner.
- **Fix hint:** On the DSR side, additively mirror the value under the key the bridge expects: in submitAudit() write `audit = { approved, total, score: total, ...scores, ... }`. Cannot edit the bridge; mirroring satisfies the existing consumer with no schema change.

## [P2] dsr-bug-07 — W2-3 duplicate QMS sale row when visitor marked Purchase but bill/amount left blank (cross-day / reassigned CRO)
- **Module/area:** dsr | **Confidence:** medium
- **Location:** dsr.html visitorPurchase() lines 1984-2003 (same-day dedup only, on current rec.sales); bridge cross-day guard integration-bridge.js consumeQmsToDsr lines 202-214 relies on DSR_PURCHASE gated by bill+amount lines 153-158
- **Defect:** When a CRO marks a QMS walk-in as Purchase, visitorPurchase() pushes a qms-visitor sale row with EMPTY billNo/amount and dedups only within the current record's rec.sales (line 1992). The bridge's cross-day/reassigned-CRO anti-echo (dsrPurch set) is populated ONLY from DSR_PURCHASE events, which the emitter fires ONLY when bill AND amount are present (integration-bridge.js:156 `if(!_bill||_amt<=0) return;`). So if the CRO marks Purchase but never fills the bill, and the SM later closes that lead as SALE in QMS, SALE_CLOSED files a SECOND 'qms' sale row into the record that owns the close-day (cross-day: entry yesterday, close today; or reassigned CRO: different staff record). hasRef() only guards the same-day record, so the customer's purchase appears twice.
- **Evidence:** visitorPurchase dedup scoped to current rec.sales (1992); bridge DSR_PURCHASE gate `if(!_bill||_amt<=0) return;` (integration-bridge.js:156); anti-echo comment 'hasRef() below only guards the SAME-DAY record' (integration-bridge.js:204)
- **Impact:** Double-counted sale for a QMS-linked customer when the CRO leaves bill/amount blank — inflates bill count and (once amounts entered) sales totals in DSR and DSR-derived roll-ups. Bounded to the blank-bill path, but that is a common real state (CRO marks purchase, forgets the bill).
- **Fix hint:** Root cause is the bridge's emit gate (not editable here). DSR-side mitigation: on render, dedup displayed sales by sourceRef across source in {'qms','qms-visitor'} so a same-cid pair collapses to one row in the list and in sales totals, and surface an SM reconcile flag rather than silently summing both.

## [P2] dsr-bug-08 — submitAudit writes a stale st.auditRec snapshot → can clobber bridge additions made after selection
- **Module/area:** dsr | **Confidence:** medium
- **Location:** dsr.html selectAudit() lines 2483-2504 (snapshots st.auditRec via JSON.parse), submitAudit() line 2666 saveRec(st.auditRec), resetAudit() line 2673
- **Defect:** selectAudit() parses the record into st.auditRec once. If the bridge appends a QMS sale/visitor to that same key between selecting the record and the SM pressing Approve/Reject, submitAudit() writes the STALE st.auditRec (plus the new audit object) back with saveRec(), dropping the bridge's addition. Same whole-blob overwrite pattern as bug-02 but on the SM side.
- **Evidence:** st.auditRec set from JSON.parse at selectAudit (2488/2496); submitAudit `saveRec(st.auditRec)` (2666) with no re-read
- **Impact:** A QMS sale/visitor injected during the SM's audit window is silently discarded when the SM approves/rejects. Rare (needs a late close during the audit window) but a data-loss path on an already-submitted day.
- **Fix hint:** Before saveRec in submitAudit/resetAudit, re-read the stored record and merge only the audit field onto the fresh copy (or union new qms* rows by sourceRef) instead of writing the snapshot wholesale. Additive.

## [P3] dsr-bug-09 — Visitor sourceRef interpolated into inline onclick without escaping single quotes
- **Module/area:** dsr | **Confidence:** medium
- **Location:** dsr.html renderVisitors() lines 1973-1974 `onclick="visitorPurchase('${sref}')"` / visitorNonPurch('${sref}'); sref=esc(String(v.sourceRef)) line 1956; esc() line 1414
- **Defect:** esc() escapes & < > " but NOT the single quote. sref is placed inside a single-quoted JS string literal in the inline onclick. If a QMS customer id ever contains a single quote or backslash, the onclick breaks (JS syntax error) and Purchase/Non-purchase buttons stop working for that row; a crafted value could inject JS. QMS cids are normally numeric/uuid, so exploitability is low, but the same-attribute pattern was deliberately avoided elsewhere (selectAuditFromEl uses data-* for exactly this reason).
- **Evidence:** renderVisitors buttons 1973-1974 interpolate sref into single-quoted onclick; esc() (1414) does not escape ' ; contrast selectAuditFromEl comment 2475-2479
- **Impact:** Purchase/Non-purchase buttons non-functional (or JS-injectable) for any visitor whose sourceRef contains a quote/backslash. Very low likelihood given QMS id format.
- **Fix hint:** Reuse the data-attribute + delegated-handler pattern from selectAuditFromEl: the row already has data-vref="${sref}"; read it in the handler instead of interpolating sref into the onclick string. Additive, no libraries.
