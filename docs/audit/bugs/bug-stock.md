## [P1] stock-carryforward-early-return — Opening carry-forward abandons the 7-day lookback at the first prior day that exists but is not closing-locked
- **Module/area:** stock | **Confidence:** high
- **Location:** prefillOpeningFromPrev(), stock.html lines 971-981 (loop 'for (let back=1; back<=7; back++)', bail at line 975)
- **Defect:** The loop is documented to 'seed each brand's Opening System from the most recent prior day's LOCKED closing physical counts (looks back up to 7 days).' In reality, after `if (!raw) continue;` skips empty days, the very first prior day that HAS a stored blob is tested with `if (!prev || prev.closingLocked !== true || !prev.closing) return d;`. Because this is `return d` (not `continue`), an existing-but-unlocked prior day terminates the whole lookback. Concrete repro: Monday register is filled and its closing is LOCKED. Tuesday the register is opened (a blob exists) but the SM forgets to lock Tuesday's closing. Wednesday morning, opening carry-forward should pull Monday's locked closing physical, but back=1 (Tuesday) exists and is unlocked, so the function returns immediately and seeds NOTHING — even though back=2 (Monday) is a valid locked source. The owner sees blank Opening System for every brand and must re-key the entire opening count, defeating the feature and inviting transcription errors in the opening figure that feeds closingSys and the whole day's variance.
- **Evidence:** for (let back = 1; back <= 7; back++) { const raw = localStorage.getItem(...prevDateStr(st.date, back)); if (!raw) continue; const prev = JSON.parse(raw); if (!prev || prev.closingLocked !== true || !prev.closing) return d; brands.forEach(...); return d; }
- **Impact:** Carry-forward silently produces no opening stock whenever the immediately-preceding day was used but left unlocked, forcing full manual re-entry and risking a wrong opening figure that propagates to closing-system and variance. This is exactly the 'opening carry-forward correctness across the day boundary' hot spot.
- **Fix hint:** Change the bail-out to skip only the non-locked day, not the whole loop: replace `if (!prev || prev.closingLocked !== true || !prev.closing) return d;` with `if (!prev || prev.closingLocked !== true || !prev.closing) continue;` so the loop keeps walking back to the most recent LOCKED day (up to 7). Keep the `return d` only after a successful seed.

## [P2] stock-carryforward-unpersisted — Prefilled opening System Stock is shown but never persisted unless the user edits an OPENING field
- **Module/area:** stock | **Confidence:** medium
- **Location:** prefillOpeningFromPrev()/loadData() lines 962-984, 923-939; untouched predicate line 966-969
- **Defect:** Carry-forward mutates `d.opening[b].systemStock` in memory but loadData() never saves. The comment says it is 'persisted by the normal save on the user's first edit.' The `untouched` gate only inspects opening fields (systemStock/isCounted/croName), so a user who works ONLY in Day Movements and Closing (never touching an opening cell) leaves opening systemStock unsaved. Concrete consequence: the on-screen Opening System, closingSys (= opening + inward + grn - outward - sales - theft), and the whole Summary all use the prefilled value, but the raw stored blob keeps systemStock:null. If the carry-forward SOURCE day is later edited or unlocked, the CURRENT day's opening figure silently changes on next load, and the integration bridge (which reads the raw blob, not loadData) never sees the prefilled opening at all. So the same day can show one opening total in the UI/export and a different one in storage.
- **Evidence:** const untouched = brands.every(b => { const o = d.opening[b]; return !o || (o.systemStock === null && !isCounted(o) && !o.croName); }); ...  brands.forEach(b => { const t = totalPhys(prev.closing[b]); if (t !== null && d.opening[b]) d.opening[b].systemStock = t; });  // never saveData
- **Impact:** A day's opening (and therefore closing-system and variance) can silently change after the fact, and the persisted record disagrees with what the owner saw/printed. Non-catastrophic because the recompute is deterministic, but it is a genuine state-desync of a money-adjacent figure.
- **Fix hint:** When prefillOpeningFromPrev actually seeds a value into an as-yet-unsaved today (not a past view, not locked), persist immediately (saveData(d) inside the seed branch) so the record and UI agree and the value can't drift when the source day changes. Guard with isPastView() as already done.

## [P2] stock-reopen-mov-closing-stale — Re-opening Day Movements after Closing is locked lets movements change while the locked closing count is now stale and unreachable
- **Module/area:** stock | **Confidence:** medium
- **Location:** reopenMovements() lines 1868-1877; updateClosingTabState() 1880-1888; updMov() closingSys recompute 1679-1682
- **Defect:** reopenMovements() sets movementsSubmitted=false but does not touch closingLocked. If the SM had already locked Closing (closingLocked=true) and then re-opens movements, the movements inputs become editable (they are disabled only on `data.movementsSubmitted || isPastView()`), so the SM can change Sales/Inward/etc. Each edit recomputes closingSys via updCloseSysCell, so the LOCKED closing's variance silently shifts to reflect movements the closing count was never reconciled against. Meanwhile the Closing tab becomes tab-locked again (updateClosingTabState sets tab-locked when !submitted), so the SM cannot open Closing to re-verify or re-count without re-submitting. The printed/summary closing variance for a 'locked' day is therefore mutable and can end up inconsistent with the physical count that was locked.
- **Evidence:** function reopenMovements(){ ... data.movementsSubmitted = false; saveData(data); ... toast('Day Movements re-opened for editing. Closing Stock is locked.','warn'); }  // closingLocked untouched; movements inputs re-enabled; closingSys recomputes
- **Impact:** The 'locked' closing figure and its variance can be changed indirectly through movements while the closing count itself is frozen and inaccessible — a wrong-but-not-catastrophic variance can be shown to the owner for a day believed to be finalised.
- **Fix hint:** On reopen, either also clear closingLocked (and toast that closing is unlocked for re-count), or block movement edits while closingLocked is true, so the locked closing count and the movements that feed its system figure can't diverge. Update the toast text accordingly.

## [P2] stock-bridge-rollup-race — Integration bridge writes _dsrRollup into the same stock blob with a read-modify-write that can clobber a concurrent user edit
- **Module/area:** stock (cross-module with integration-bridge.js) | **Confidence:** low
- **Location:** integration-bridge.js consumeDsrToStock() lines 302-317 (reads 'saagar_stock_'+skey(sc)+'_'+d, adds sb._dsrRollup, S(sk,sb)); vs stock.html saveData() line 985
- **Defect:** The bridge's consumeDsrToStock does L(sk) -> sb._dsrRollup = {...} -> S(sk, sb), a whole-blob read/modify/write on the SAME localStorage key the stock module owns. The bridge runs on a 60s tick, on every 'storage' event, and 50ms after any module iframe load (safeCycle). The stock module also does whole-blob loadData()->mutate->saveData() on every field onchange. If a user's saveData lands between the bridge's L(sk) and its S(sk,sb), the bridge's stale copy overwrites the user's just-saved cell (and vice-versa the user's save can drop _dsrRollup). Both are last-writer-wins over a non-atomic RMW; the debounce/tick reduce but do not eliminate the window described in the module's own historic ANR/desync crash class.
- **Evidence:** var sk='saagar_stock_'+skey(sc)+'_'+d, sb=L(sk,null); if(!sb||typeof sb!=='object') sb={}; sb._dsrRollup={...}; S(sk,sb);  // whole-blob overwrite of the key stock's saveData(d) also owns
- **Impact:** A stock cell edit made in the ~ms window around a bridge cycle can be silently reverted (or the DSR roll-up dropped), i.e. lost data. Rare in practice but a real race between the ~60s bridge tick and user writes on a shared blob.
- **Fix hint:** Cannot edit storage-core; within allowed scope, have the bridge merge into the freshest blob only (re-read immediately before write) and write ONLY the _dsrRollup sub-key by re-loading right before S(); or move _dsrRollup to a SEPARATE additive key (e.g. saagar_stock_dsrrollup_<store>_<date>) that stock reads for display but never rewrites, eliminating the shared-blob RMW entirely.

## [P2] stock-bid-collision — bid() can collapse two distinct brand names to the same DOM id, routing edits to the wrong brand
- **Module/area:** stock | **Confidence:** medium
- **Location:** bid() line 2286, getBrandByBid() lines 2290-2292, addBrand() normalisation line 2027
- **Defect:** bid(brand)=brand.replace(/\s+/g,'_').replace(/[^A-Za-z0-9_]/g,'') strips all non-alphanumeric/underscore characters. addBrand only uppercases and trims (no special-char stripping), so an SM can add brands like 'R&D' and 'R/D', or 'G-SHOCK PRO' and 'G SHOCK PRO', that collapse to identical bids ('RD', 'GSHOCKPRO'). getBrandByBid then does getBrands().find(br => bid(br)===b) and returns the FIRST match. All inline handlers (updOpen/updClose/updMov/updCountDone) pass bid(brand); the reverse lookup therefore resolves the second colliding brand to the first, so counts typed for one brand are written to the other, and their row DOM ids (row-open-<bid>, cl-sys-<bid>) collide so only one row's computed cells update.
- **Evidence:** function bid(brand){ return brand.replace(/\s+/g,'_').replace(/[^A-Za-z0-9_]/g,''); }  function getBrandByBid(b){ return getBrands(st.store).find(br=>bid(br)===b)||b; }  addBrand: const n=inp.value.trim().toUpperCase();
- **Impact:** With special-character brand names an edit can be saved against the wrong brand and computed cells stop updating for the collided row — silently wrong stock figures. Requires an unusual brand name so probability is low, but the failure is a data-integrity one.
- **Fix hint:** Make the row identity collision-proof: key DOM ids and the reverse lookup by the brand's index in getBrands() (or a per-render unique token) instead of a lossy slug, or reject/auto-suffix duplicate bids in addBrand. Keep esc() for display.

## [P3] stock-loaddata-missing-section — loadData() throws and silently discards a stored blob that is missing a top-level opening/closing/movements section
- **Module/area:** stock | **Confidence:** low
- **Location:** loadData() migrate loop lines 929-936 (d.opening[b] / d.closing[b] deref), catch swallow line 936
- **Defect:** The migrate loop dereferences d.opening[b] and d.closing[b] without checking that d.opening/d.closing exist. If a stored blob is missing a section (hand-edited storage, a truncated write, or a foreign import), the loop throws a TypeError which is swallowed by the surrounding try/catch, and loadData falls through to `return prefillOpeningFromPrev(initData())` — a fresh empty object. The blob's other sections (e.g. real movements/closing that WERE present) become invisible, and the next saveData() overwrites the key with the fresh init, permanently losing them.
- **Evidence:** getBrands(st.store).forEach(b => { if (d.opening[b] && ...) ...; if (d.closing[b] && ...) ...; }); ... } catch(e){} } return prefillOpeningFromPrev(initData());
- **Impact:** Edge-case data loss on a malformed/partial blob. The module never produces such a blob itself and importJSON normalises all three sections, so this only triggers on externally corrupted storage — hence low severity.
- **Fix hint:** Guard the migrate loop against missing sections (e.g. if (!d.opening||!d.closing||!d.movements) treat as corrupt and preserve/normalise rather than deref), or normalise the parsed blob through the same section-ensuring path importJSON uses before touching d.opening[b].
