## [P1] cro-dup-audit — No duplicate-audit guard — same CRO/date/store can be saved repeatedly, double-counting all dashboard KPIs
- **Module/area:** cro_audit | **Confidence:** high
- **Location:** submitAudit() lines 1214-1256 (all.unshift(audit) at 1250) — no pre-insert dedup against getAudits()
- **Defect:** submitAudit() always appends a brand-new record (id:'a'+Date.now()) with no check for an existing audit having the same date+store+cro. Repro: fill+submit an audit for CRO 'Ravi', Titan World, 2026-07-03 (score e.g. 80). Without leaving the tab, resetForm clears fields, re-enter the SAME Ravi/store/today and submit again. Two separate records now exist for the same person/day. Every dashboard aggregate then double-counts: renderWeekDash/renderMonthDash sum a.tasks.t5.npsCollected, billsCount, t6.reviewsCount, t7.activityCount across BOTH records (lines 1428-1431, 1514-1517), and groupByCRO averages the CRO's total twice (line 1636). The code's own comment at line 1215 ('the model APPENDS, so a back-dated submit would duplicate') and loadPreData excluding today's audits (a.date!==today, lines 815-816) show the author knew re-submits duplicate but only guarded the pre-fill, not the store. Owner sees inflated survey/bill/review counts and skewed CRO averages.
- **Evidence:** const all=getAudits(); all.unshift(audit); localStorage.setItem('cro_audits_v3',JSON.stringify(all));  // no find()/dedup anywhere (grep for a.date===/a.cro=== returns nothing)
- **Impact:** Wrong KPI figures and CRO averages shown to owner on Dashboard; response-rate and survey totals inflated by the number of accidental re-submits. Data integrity of the audit ledger degraded (no idempotency).
- **Fix hint:** In submitAudit(), before all.unshift(audit), check getAudits() for an existing record with same date+store+cro; if found, either confirm-and-replace (splice out the old id) or block with a toast. Keep additive/localStorage-only.

## [P1] cro-groom-stale — Auto-filled grooming % is NOT cleared when CRO is changed to one without a checklist — wrong CRO's grooming score is stored
- **Module/area:** cro_audit | **Confidence:** high
- **Location:** autoFillGrooming() lines 1865-1880 — the else (feed-miss) branch at 1876-1879 never resets inp.value or recomputes t9
- **Defect:** onCroDateChange() (fired on every #f-cro keystroke, line 537) calls autoFillGrooming(). When the typed CRO has a grooming feed entry, it sets #groom-pct, marks it readOnly, and scores t9 (e.g. 90% -> 9/10). If the SM then edits the CRO name to a DIFFERENT person who has NO feed grooming entry, the else branch runs: it only sets readOnly=false and shows the 'manual' note. It does NOT clear inp.value and does NOT call onGroomInput(), so #groom-pct still shows 90 and tData.t9.groomingPct stays 90, still scored 9/10. Repro: type 'Ravi' (feed grooming 90%) -> box auto-fills 90, t9=9/10; change name to 'Amit' (no feed) -> box still shows 90, t9 still 9/10, box now editable so it looks legitimate. If the SM submits without noticing, Amit's audit is saved with Ravi's grooming score. Confirmed against integration-bridge.js: feed is keyed feed[date][kk(name)] with groomingPct default null (line 380), so switching name genuinely changes feed presence.
- **Evidence:** }else{ inp.readOnly=false; inp.classList.remove('ro'); setGroomNote('manual','no checklist — enter manually'); }  // no inp.value reset, no onGroomInput()
- **Impact:** A stored audit can carry another employee's grooming score (wrong per-task score and wrong total /100). Easy to miss because the pre-populated, now-editable field looks like normal manual entry.
- **Fix hint:** In the else branch of autoFillGrooming(), when there is no auto value, reset inp.value='' (and tData.t9.groomingPct=0) and call onGroomInput() so the score display and stored data clear. Only clear when the value was previously auto (track a flag) so a manually-typed value isn't wiped.

## [P2] cro-backdate-picker — Date picker allows back-dating an audit to any past day while viewing today, bypassing the read-only-past guard and enabling arbitrary-date duplicates
- **Module/area:** cro_audit | **Confidence:** medium
- **Location:** submitAudit() lines 1230/1244 (date = #f-date input value) and stApplyReadOnly() lines 1772-1773 (only disables #f-date when stIsPast())
- **Defect:** The read-only-past protection keys on stViewDate() (the shell's view date), not on the value chosen in the #f-date input. While viewing the real today, #f-date is enabled and the SM can pick any earlier (or future) date; submitAudit reads that value verbatim into audit.date. So audits can be filed under arbitrary past/future dates from the live screen. Combined with the missing duplicate guard, this lets multiple records accumulate on any chosen date, landing them in past weeks/months on the Dashboard and History. It also defeats the app's 'entries filed under the local date' convention.
- **Evidence:** const date=document.getElementById('f-date').value; ... audit={ id:'a'+Date.now(), date, ...}  // #f-date only disabled when stIsPast(), not when the picked date is in the past
- **Impact:** Audits can be mis-filed to wrong dates and duplicated onto past periods, skewing historical weekly/monthly KPIs the owner reviews.
- **Fix hint:** Either constrain #f-date (min/max = stViewDate) or validate in submitAudit that date===stViewDate() (or within an allowed window) before saving; show a toast otherwise. Additive only.

## [P2] cro-nps-score-unclamped — NPS Score input is not clamped to 100 — an out-of-range value inflates the owner-facing 'Avg NPS Score' KPI
- **Module/area:** cro_audit | **Confidence:** medium
- **Location:** onNpsInput() line 1068 (score=+value||0, no clamp); stored at 1077; averaged in renderWeekDash/renderMonthDash lines 1432-1433 / 1518-1519
- **Defect:** The NPS-score field has max=100 in markup (line 946) but onNpsInput does score=+document.getElementById('nps-score-inp').value||0 with no upper clamp; some browsers/paste paths allow values >100 to reach the handler. scorePts is safely capped via Math.min(...,5) so the task score is unaffected, but the raw npsScore is stored and later averaged for the 'Avg NPS Score' KPI with no cap. Repro: enter NPS score 150 -> stored npsScore:150 -> Dashboard 'Avg NPS Score' shows e.g. 150.0 against a Target of >=85, a nonsensical figure to the owner.
- **Evidence:** const score = +document.getElementById('nps-score-inp').value||0;  // no Math.min(...,100)
- **Impact:** Owner can see an impossible average NPS (>100) on the Dashboard for weeks/months containing an over-range entry.
- **Fix hint:** Clamp on read: const score=Math.min(Math.max(+value||0,0),100); apply the same clamp when reading bills/coll for sanity. Additive.

## [P3] cro-week-def-mismatch — Month dashboard week breakdown uses a different week definition than the Weekly dashboard, so audits can appear in inconsistent 'Week N' buckets
- **Module/area:** cro_audit | **Confidence:** medium
- **Location:** buildWeekBreakdown() line 1594-1596 (wkNum, Jan-1/Sunday-based) vs getWeekRange() line 1390-1396 (Monday-Sunday ranges)
- **Defect:** The Weekly dashboard groups audits by Monday-Sunday ranges (getWeekRange). The Monthly dashboard's 'Week-by-Week Breakdown' groups by wkNum(d) = Math.ceil(((d-j)/864e5+j.getDay()+1)/7), a Jan-1/Sunday-anchored US-style week number. The two systems disagree at week boundaries (e.g. an audit dated on a Sunday can fall in a different 'Week N' between the two views), and wkNum can also assign the same calendar week two different numbers across a month boundary. Purely a labeling/grouping inconsistency — no data loss — but confusing when cross-checking weekly vs monthly views.
- **Evidence:** buildWeekBreakdown: const wn=wkNum(d);  vs  weekly dash: getWeekRange(dashOff) start=Monday
- **Impact:** Confusing/inconsistent week labels and week totals between the Weekly tab and the Monthly week-breakdown; owner may think numbers don't reconcile.
- **Fix hint:** Use one week definition everywhere — derive week buckets from getWeekRange (Monday-Sunday) in buildWeekBreakdown instead of wkNum, or document that the two use different week systems.

## [P3] cro-rr-uncapped-display — Dashboard response-rate % is uncapped, so a surveys>bills data-entry mistake shows >100% to the owner
- **Module/area:** cro_audit | **Confidence:** medium
- **Location:** renderWeekDash line 1434 (wkRR) and renderMonthDash line 1520 (mRR); per-CRO rr lines 1471/1565
- **Defect:** Response rate on the dashboard is Math.round(totSur/totBills*100) with no upper bound. If an SM logs more NPS surveys than bills for a day (fat-finger), the aggregated week/month response rate renders above 100% (e.g. 130%). The task score is unaffected (ratePts capped at 5), but the KPI card and per-CRO 'Rate' chip display an impossible percentage.
- **Evidence:** const wkRR = totBills>0?Math.round(totSur/totBills*100):0;  // no Math.min(...,100)
- **Impact:** Cosmetic/credibility: owner sees a >100% response rate figure on the Dashboard.
- **Fix hint:** Cap the displayed rate: Math.min(Math.round(totSur/totBills*100),100) for the KPI text (or flag the anomaly). Scoring already caps, so display-only change.
