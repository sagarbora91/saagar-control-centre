## [P0] bug-payroll-01 — Locked-run snapshot keyed by empId||name collapses duplicate employees → wrong frozen pay shown to owner
- **Module/area:** payroll | **Confidence:** high
- **Location:** payroll.html lockRun() line 3011 (snapshot[empKeyOf(row)]=calcGM(row)); consumed by gmComputed() lines 1730-1737 and empKeyOf() line 1693
- **Defect:** lockRun() builds the frozen snapshot as an object keyed by empKeyOf(row) = String(row.empId||row.name).trim().toLowerCase(). Two GM employees can legitimately share that key: (a) same Emp ID typed twice (the module KNOWS this happens — checkGlobalValidation() line 1915-1916 emits a 'Duplicate Employee ID' WARNING, not a blocking error, and lockRun only blocks on slipRecords err-status, not on duplicate keys), or (b) two blank-empId rows with the same name, or (c) two rows with blank empId AND blank name (key=''). On lock, the second row overwrites the first in snapshot{}. After locking, gmComputed() serves run.snapshot[empKeyOf(row)] for BOTH rows, so both employees display the SECOND employee's salary/net/advance in the Saagar Traders sheet, Approval table, Salary Slips, Reports and every PDF. Concrete repro: two employees both with Emp ID 'E1' (or both blank), different gross; lock the run; both slips/register rows now show identical pay = the second one's. Owner pays and files statutory returns off wrong per-employee figures. Also advRecovered is keyed by voucher id so it survives, but the per-employee snapshot money is corrupted.
- **Evidence:** empKeyOf: function empKeyOf(row){return String(row.empId||row.name||"").trim().toLowerCase();}  |  lock: gmRows().forEach(row=>{ snapshot[empKeyOf(row)]=calcGM(row); });  |  serve: const s=run.snapshot[empKeyOf(row)]; if(s) return s;  |  duplicate is only a 'warn': issues.push({type:"warn",text:`Duplicate Employee ID ...`})
- **Impact:** Wrong money figure shown (and paid/filed) for one of two same-keyed employees in every locked view/PDF; silent, only visible if the owner cross-checks names. Data-integrity loss on the frozen pay-run.
- **Fix hint:** Before locking, detect snapshot-key collisions among gmRows() (duplicate empKeyOf, including empty keys) and treat them as a BLOCKING error in runBlockingErrors()/lockRun() with a clear 'two employees share ID/blank identity — give each a unique Emp ID' message. Alternatively key the snapshot by a guaranteed-unique id (row.id when non-zero, else global index) instead of empId||name — but gmComputed lookup must use the same key, and note row.id can be 0 for legacy rows (see normalizeRow line 1567 / slipRecords comment lines 2332-2334, which already avoided row.id for exactly this reason).

## [P1] bug-payroll-02 — Advance mid-month import Absent proposal caps at today's date only when payroll month == real calendar month → date-boundary mis-proration
- **Module/area:** payroll | **Confidence:** medium
- **Location:** payroll.html attFeedDiff() lines 3149-3164 (out.baseDays and prop.absent)
- **Defect:** attFeedDiff() computes baseDays = (fk===curFk) ? Math.min(td, now.getDate()) : td, where fk is the PAYROLL month key (attFeedKey from state.meta.month/year) and curFk is the REAL calendar month (new Date()). Proposed Absent = max(0, baseDays − present − leave − half). The intent (comment lines 3138-3143) is to avoid marking every not-yet-elapsed day absent for the in-progress current month. But the gate is month-equality only. Failure cases: (1) Payroll is being run for the PREVIOUS month (very common — you close Jan payroll in early Feb): fk='2026-01' != curFk='2026-02', so baseDays=td=31 and Absent is correctly full-month — OK. (2) But if the user leaves state.meta.month on the current calendar month while the DSR feed is still sparse (feed only has the first few days), importing marks the rest of the month Absent unless it happens to be the same calendar month AND now.getDate() luckily matches — and Math.min(td, now.getDate()) uses getDate() (calendar day 1-31) against td which is a WORKING-days count net of holidays, so on a month with holidays baseDays can exceed the true elapsed working days, over-counting Absent. (3) Around the 00:30 new-day rule: now.getDate() flips at real local midnight, not at the app's ~00:30 boundary, so an import run between 00:00 and 00:30 uses the NEW day number while entries are still filed under the previous local date — off-by-one elapsed day in the Absent proposal.
- **Evidence:** const now=new Date(); const curFk=now.getFullYear()+"-"+String(now.getMonth()+1).padStart(2,"0"); out.baseDays=(fk===curFk)?Math.min(td,now.getDate()):td;  ... absent:Math.max(0,roundHalf(out.baseDays-safeN(f.present)-safeN(f.leave)-safeN(f.half)))
- **Impact:** Imported Absent days (hence salary days and net pay) can be over- or under-stated by 1+ day for the in-progress month; a maker who trusts the diff and locks propagates the error to pay. Workaroundable: the maker reviews the diff and can hand-edit, so not silent data loss.
- **Fix hint:** Base the elapsed-day cap on elapsed WORKING days (respecting holidays) rather than calendar getDate(), and derive 'today' from the same local-date key the rest of the app files entries under (stRealToday()/the app's 00:30 rule) rather than raw new Date().getDate(). Consider caching a stable 'as-of' day at import time so a cross-midnight import is deterministic.

## [P1] bug-payroll-03 — closeMonth into an already-locked target month silently downgrades that month's lock to draft, keeping a stale snapshot
- **Module/area:** payroll | **Confidence:** medium
- **Location:** payroll.html closeMonth() lines 3031-3045, esp. line 3041 ensureRun(curKey()).status="draft";
- **Defect:** closeMonth() advances state.meta.month/year to the next month, then does ensureRun(curKey()).status="draft". ensureRun (line 2849) returns the EXISTING run object if one exists. If the target next month was previously locked (e.g. the user closed forward, later Unlocked+re-navigated, or navigated back and re-closed), that run already has status='locked' with a frozen snapshot and advRecovered. closeMonth flips only .status to 'draft' but LEAVES run.snapshot and run.advRecovered in place. Now: gmComputed() (line 1732 checks run.status==="locked") no longer serves the snapshot, so figures recompute live — but archiveKeys()/renderArchive still won't list it (status!=='locked'), AND advRecoveredBefore() (line 1703 requires status==='locked') stops counting that month's already-recorded advance recoveries, so vouchers can be re-scheduled/double-recovered in later months. The month's approver/lockedAt/formulaVersion metadata is also silently retained on a now-'draft' run. There is no confirm about clobbering an existing locked run for the target month.
- **Evidence:** function ensureRun(k){state.runs=state.runs||{};if(!state.runs[k])state.runs[k]={status:"draft"};return state.runs[k];}  ... closeMonth: state.meta.month=nm;state.meta.year=ny; ensureRun(curKey()).status="draft";
- **Impact:** A previously-locked month can be silently un-locked (audit trail + frozen figures lost) and its advance recoveries stop counting, letting the same advance be recovered again downstream. Rare (requires navigating/closing into a month that already has a locked run) but corrupts money + audit state.
- **Fix hint:** In closeMonth(), if the target month's run already exists with status==='locked', refuse or require an explicit unlock-first confirmation instead of blindly setting status='draft'. When intentionally resetting to draft, also clear/relocate snapshot and advRecovered so advRecoveredBefore stays consistent.

## [P2] bug-payroll-04 — advVoucherNo() derives voucher number from array length → duplicate voucher numbers after any deletion
- **Module/area:** payroll | **Confidence:** high
- **Location:** payroll.html advVoucherNo() line 2615, used by createAdvance() line 2653
- **Defect:** advVoucherNo() returns `GM/ADV/<year>/<(advances.length+1) padded>`. The sequence is derived from the current array length, not a monotonic counter. Repro: create vouchers 001, 002, 003 (length 3). Delete 002 (delAdvance, length now 2). Create a new voucher → length+1 = 3 → 'GM/ADV/2026/003', duplicating the existing 003's voucher number. Two distinct vouchers now share a printed Voucher No. on their PDFs and in the ledger. The voucher's internal id (++state.nextId) is still unique so recovery math is unaffected, but the human-facing document number collides.
- **Evidence:** function advVoucherNo(){return `GM/ADV/${safeN(state.meta.year)}/${String((state.advances||[]).length+1).padStart(3,"0")}`;}
- **Impact:** Duplicate advance-voucher numbers on printed/shared PDFs and the Advances ledger after any deletion; confusing for reconciliation, but no money mis-calc.
- **Fix hint:** Derive the sequence from a persisted monotonic counter (e.g. reuse state.nextId, or a dedicated state.nextAdvSeq that only increments), not from (state.advances.length+1). Optionally scope the counter per year.

## [P2] bug-payroll-05 — advMatch matches an advance to the wrong employee when empId is blank and two employees share a name
- **Module/area:** payroll | **Confidence:** medium
- **Location:** payroll.html advMatch() lines 1694-1698; advanceForRow() lines 1723-1727
- **Defect:** advMatch(a,row) matches on empId when both sides have one, else falls back to name equality: (!aEid && aNm && aNm===nm) || (!eid && aNm && aNm===nm). If a voucher was created for an employee who had a blank Emp ID (createAdvance stores row.empId which can be ''), the voucher matches by name only. If two GM employees share the same name (allowed — no uniqueness enforced), the advance is deducted from BOTH of them (advanceForRow sums per row), or from whichever the name-only branch hits, over-recovering the advance. Combined with finding 01 (duplicate-key employees), the same advance amount is subtracted from two people's Final Pay.
- **Evidence:** return (eid&&aEid&&eid===aEid)||(!aEid&&aNm&&aNm===nm)||(!eid&&aNm&&aNm===nm);  ... (state.advances||[]).forEach(a=>{ if(advMatch(a,row)) sum+=advScheduled(a,m,y); });
- **Impact:** An advance can be double-deducted across two same-named employees, understating each one's take-home. Requires blank empId + duplicate name, so uncommon, but silently wrong money.
- **Fix hint:** Encourage/enforce unique Emp IDs (see finding 01) and prefer id-based advance linkage; when falling back to name, guard against matching more than one row (e.g. skip name-only match when the name is non-unique among gmRows).

## [P2] bug-payroll-06 — loadState prefers embedded seed over saved localStorage → user edits silently discarded on reload when a non-empty seed is baked in
- **Module/area:** payroll | **Confidence:** medium
- **Location:** payroll.html loadState() lines 1615-1620
- **Defect:** loadState() reads the embedded <script id='app-data'> seed first: if(Array.isArray(emb.rows)&&emb.rows.length>0){ state=normalizeState(emb); ...overwrite localStorage... ; return; }. It only falls through to the saved localStorage snapshot when the embedded seed has ZERO rows. The shipped seed (line 698) has rows:[] so today it loads from localStorage — but any build/snapshot that bakes employee rows into #app-data (downloadSnapshot() rewrites #app-data with the full current state, line 2284) will, when reopened, ALWAYS reload the baked seed and clobber whatever the user later saved to localStorage under the same STORAGE_KEY. On a demo/seeded APK whose #app-data is pre-populated, every reload throws away the accountant's edits from the previous session.
- **Evidence:** if(Array.isArray(emb.rows)&&emb.rows.length>0){state=normalizeState(emb);if(!ST_READ_ONLY){try{mirrorRowOutputs();localStorage.setItem(STORAGE_KEY,JSON.stringify(state));}catch(e){}}return;}  ... try{const saved=localStorage.getItem(STORAGE_KEY);state=normalizeState(saved?JSON.parse(saved):emb);...}
- **Impact:** Silent loss of user-entered payroll data across reloads on any build where #app-data is non-empty (seeded APK / opened snapshot). On the empty-seed production build this path is dormant, hence P2, but it is a latent data-loss trap for exactly the seeded builds noted in project memory.
- **Fix hint:** Decide a single source of truth: either treat the embedded seed as a first-run default only (load it only when localStorage is empty), or version the seed so a newer localStorage save wins. Do not unconditionally overwrite localStorage from the seed when a saved snapshot exists. (Additive-localStorage rule respected — only load ordering changes.)

## [P2] bug-payroll-07 — ESIC applicability tested against pro-rated grossPayable, not contractual gross → part-month employee near the ceiling flips ESIC on/off month to month
- **Module/area:** payroll | **Confidence:** medium
- **Location:** payroll.html calcGM() line 1788 (esicOn uses grossPayable<=wageCeiling)
- **Defect:** esicOn = !!row.esicApplicable && grossPayable <= (RES.wageCeiling||21000). grossPayable is the attendance-pro-rated gross (line 1772), NOT the contractual row.gross. An employee whose contractual gross is, say, 22,000 (above the 21,000 ESIC ceiling and therefore genuinely NOT an ESIC member) will, in any month with enough absence that pro-rated grossPayable drops to <=21,000, suddenly have ESIC EE (0.75%) and ER (3.25%) deducted/charged — and drop out again in a full-attendance month. ESIC membership is determined by wage, but statutorily a member above the ceiling stays in the contribution period; toggling it purely on prorated earned wage produces inconsistent deductions and a wrong net for high-absence months. (PT has an explicit PT_BASE_MODE constant acknowledging the earned-vs-contractual choice; ESIC silently uses earned with no such guard.)
- **Evidence:** const esicOn=!!row.esicApplicable&&grossPayable<=(safeN(RES.wageCeiling)||21000); const esicEE=esicOn?Math.round(esicBase*(safeN(RES.rateEE)/100)*100)/100:0;
- **Impact:** Employees near the ESIC ceiling get ESIC deducted in heavy-absence months and not in others, producing a wrong (usually lower) net and inconsistent statutory figures. Edge case (contractual gross just above ceiling + significant absence).
- **Fix hint:** Confirm the intended ESIC base with the accountant and test eligibility against the contractual row.gross (mirroring the PT_BASE_MODE decision) while still computing the contribution on the earned base if desired. At minimum expose it as a documented mode like PT_BASE_MODE rather than an implicit earned-gross test.

## [P3] bug-payroll-08 — Bank CSV net-amount rounding differs from the slip/register net (Math.round of finalPay vs penny-reconciled net) → bank transfer can be off by ₹1 from the payslip
- **Module/area:** payroll | **Confidence:** medium
- **Location:** payroll.html reportBankCsv() line 3080 (Math.round(c.finalPay)) vs gmSlipData()/buildGmSlip penny-reconciled dNet lines 2444-2447 / 2480-2484
- **Defect:** The salary slip deliberately penny-reconciles net as dEarnings − (rPt+rPf+rEsic+rAdv) where each component is rounded once (buildGmSlip lines 2479-2484, gmSlipData 2444-2447). The Bank Disbursement CSV instead writes Math.round(c.finalPay), where finalPay=netPayable+otAmount−advance is rounded as a single sum. Because the slip rounds each deduction line independently and the CSV rounds the aggregate, the two can differ by ₹1 for structured-salary employees. The amount actually transferred to the bank (from the CSV) then disagrees by ₹1 with the amount printed on the employee's payslip.
- **Evidence:** reportBankCsv: ...r.ifsc||"",Math.round(c.finalPay)].join(",")  vs  slip: const dNet=dEarnings-dDeductions; (dEarnings, dPt,dPf,dEsic,dAdv each rfix'd once)
- **Impact:** Occasional ₹1 mismatch between the bank transfer file and the printed payslip net; trivial money impact but can trigger reconciliation queries.
- **Fix hint:** Compute the bank CSV net from the same penny-reconciled figure used on the slip (reuse gmSlipData(rec).net) rather than Math.round(c.finalPay), so the CSV, slip and register all agree to the rupee.
