## [P2] tax-bug-1 — Firm name / PAN / GSTIN inserted unescaped into innerHTML in renderFirmList (stored HTML/DOM injection)
- **Module/area:** tax | **Confidence:** high
- **Location:** renderFirmList(), tax.html lines 2002-2012 (esp. `<div class="firm-name">${f.name}</div>` line 2005 and `${f.pan}`/`${f.gstin}` line 2006)
- **Defect:** The Manage-Firms modal builds its firm list with a template literal that interpolates user-typed fields directly into el.innerHTML WITHOUT escapeHtml: f.name (line 2005), f.pan and f.gstin (line 2006), and f.entity. Concrete repro: open ⚙ Firms, create a firm with name `<img src=x onerror=alert(document.cookie)>` (or `<script>`-equivalent via an <img>/<svg onload>), Save, then reopen the Firms modal — renderFirmList runs and the payload executes in the module iframe. Every OTHER place that prints a firm name in this file correctly escapes it (populateMasterFirmSelect line 2123 uses escapeHtml; calendar header line 2973 escapeHtml(f.name); Action Center escapeHtml(r.firm); dashboard escapeHtml(f.name); populateFirmSelector uses textContent). renderFirmList is the lone unescaped path.
- **Impact:** Persisted markup in a firm name/PAN/GSTIN executes as HTML/JS whenever the Firms modal is opened, and malformed (non-malicious) angle brackets in a name silently corrupt the modal layout. Offline single-user app, so it is self-inflicted rather than a cross-user breach, but it is a genuine injection/robustness defect and an inconsistency with the rest of the module.
- **Fix hint:** Wrap the three user fields in escapeHtml() exactly as the other renderers do: `${escapeHtml(f.name)}`, `${escapeHtml(f.pan)}`, `${escapeHtml(f.gstin)}` (and escapeHtml(f.entity) for good measure). escapeHtml already exists in this file (line 2839). Additive, no new libraries, offline-safe.

## [P3] tax-bug-2 — confirmDone() overwrites the whole compliance record, dropping the SHELL-facing `name` and `buffer` fields materializeDueDates stamped
- **Module/area:** tax | **Confidence:** medium
- **Location:** confirmDone(), tax.html line 2946 (`fyCompliance[id]={ done:true, filedOn, notes, evidenceRef, reviewerNote, dueDate };`) vs materializeDueDates() lines 1162 & 1166-1167
- **Defect:** materializeDueDates() deliberately stamps rec.name (plain-text obligation name) and rec.buffer (T-buffer) onto each record so the SHELL can label Reports rows and schedule T-5/T-3 deadline notifications WITHOUT re-deriving the catalogue (see the explicit comment at lines 1155-1160). When the user marks an item filed, confirmDone replaces the entire record object with a fresh literal that omits name and buffer, so those two fields are lost on the done record. Repro: mark any obligation done, inspect STATE.compliance[firm][fy][id] in localStorage — name and buffer are gone. It self-heals on the NEXT renderMonth/renderDashboard because materialize backfills missing name/buffer on existing records regardless of done state, but there is a window (immediately after confirmDone, before any re-render, e.g. if the SHELL reads the blob on a boot/tax-close resync in that gap) where the record lacks the label/buffer the notification scheduler expects.
- **Impact:** Transient loss of the notification buffer and plain-text name on a just-completed item; a boot/resync landing in that narrow window would fall back to catalogue-derivation or a generic label. Low severity because it is repaired on the next render and completed items generally do not need future deadline notifications.
- **Fix hint:** Preserve the additive fields when writing the done record, e.g. spread the prior record first: `const prev=fyCompliance[id]||{}; fyCompliance[id]={ ...prev, done:true, filedOn, notes, evidenceRef, reviewerNote, dueDate };` (keeps name/buffer, still overwrites the capture fields). Purely additive.

## [P3] tax-bug-3 — ≈₹ payable estimate keyed by STATE.fyStartYear calendar year while the bridge feed is keyed to the real current month — amounts only surface on one card and can silently show nothing after an FY switch
- **Module/area:** tax | **Confidence:** medium
- **Location:** taxPayableAmount(), tax.html lines 2595-2605 (getCalendarYearForMonth(month) → prev-month key `ym`) reading getTaxPayableFeed() vs bridge buildTaxPayable writing out[ym(today())] (integration-bridge.js lines 453-468)
- **Defect:** The bridge writes exactly ONE feed record per real calendar month under key ym(today()) ('YYYY-MM' of the machine clock). The module derives the feed key from getCalendarYearForMonth(month), which depends on the user-selected STATE.fyStartYear, not on the real clock. So the ≈₹ payable chip only ever appears on the single card whose (fyStartYear-derived) prev-month equals the real current month, and if the user switches the FY selector to any year other than the one matching the machine date, getCalendarYearForMonth shifts the computed key away from the only key the bridge populated, so every payable chip disappears. The design note (lines 2570-2576) says 'Missing/zero feed → render nothing', so this fails safe (no wrong figure shown, just an absent chip), but the estimate is effectively invisible for any FY≠current and for 11 of 12 month pages.
- **Impact:** The rupee-payable helper is largely inert: it renders on at most one card at a time and vanishes entirely when browsing any non-current FY. No wrong money figure is shown (it returns null rather than a stale amount), so this is a usefulness/coverage gap, not a data-corruption bug.
- **Fix hint:** Confirm intended behaviour with the owner; if broader coverage is wanted, the module could additionally look up the feed by the item's real prior-month key independent of fyStartYear (still additive, read-only, no invented data). At minimum document that the chip is current-month/current-FY only. Do NOT invent amounts for months the bridge never wrote.

## [P3] tax-bug-4 — Archive obligationKey groups distinct filer regimes under one key — archiving 'GSTR-1'/'GSTR-3B' hides BOTH monthly and QRMP-quarterly cards together
- **Module/area:** tax | **Confidence:** medium
- **Location:** obligationKey(), tax.html lines 2462-2466 (`String(item.name).split(/[–|]/)[0].trim()`) used by isArchived()/getVisibleItems()
- **Defect:** obligationKey derives a built-in item's archive key from the leading name token before the first en-dash or pipe. 'GSTR-1 – April (Monthly Filers)' and 'GSTR-1 – Q1 (Apr–Jun) | QRMP Quarterly Filers' both reduce to key 'GSTR-1'; likewise both GSTR-3B monthly and GSTR-3B QRMP reduce to 'GSTR-3B'. Archiving one from ⚙ Manage Compliance → Built-in therefore hides the other regime too. A regular-monthly-filer user who archives the QRMP variant (or vice-versa) also loses their real obligation from the calendar and dashboard.
- **Impact:** A user intending to hide only the filer regime that does not apply to them can inadvertently hide a regime that DOES apply, so a genuinely-due return silently disappears from the calendar/Action Center. Mitigated by firm-type filtering already hiding some variants, and reversible via Restore, so low severity.
- **Fix hint:** Consider keying built-in archives on a more specific token (e.g. include the '(Monthly Filers)'/'QRMP' qualifier) or list the concrete obligation names in the archive UI so the user sees exactly what a key covers. Keep it additive; do not change stored keys for existing archived entries without a migration.
