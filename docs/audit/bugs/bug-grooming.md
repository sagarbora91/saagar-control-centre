## [P2] grm-bug-01 — CSV export has no field escaping — a CRO name with a comma/quote/newline corrupts every column
- **Module/area:** grooming | **Confidence:** high
- **Location:** grooming.html exportCSV(), lines 943-958 (row build line 949; join line 952)
- **Defect:** exportCSV builds rows then does rows.map(r=>r.join(',')).join('\n') with ZERO quoting/escaping. CRO names are free text (input #cro-inp) or come from saagar_employee_master_v1. Concrete failing input: a CRO saved as "Sharma, Rahul" (comma) produces the CSV line `2026-07-03,Sharma, Rahul,Male,100,20,20,10:15 AM` which now has 8 fields for a 7-column header — Gender column reads "Rahul", Score reads "Male", and every downstream column shifts by one for that row. A name containing a double-quote or newline breaks the file further. Owner opening the month report in Excel sees mis-aligned / wrong data for that CRO.
- **Evidence:** L949 rows.push([dateStr, r.name, ...]);  L952 const csv = rows.map(r=>r.join(',')).join('\n');  — no escaping anywhere in the function.
- **Impact:** Month-End CSV silently mis-columns any CRO whose name contains a comma, quote, or newline; owner reads wrong gender/score against the wrong name. Data-integrity defect in a reporting export.
- **Fix hint:** Add a CSV-escape helper before join: wrap each field in double-quotes and double any internal quotes when the value contains , " or newline, e.g. csvCell(v){ v=String(v==null?'':v); return /[",\n]/.test(v)?'"'+v.replace(/"/g,'""')+'"':v; } then rows.map(r=>r.map(csvCell).join(',')). Additive, no library.

## [P2] grm-bug-02 — Unescaped CRO name interpolated into innerHTML in Daily Summary and Month-End cards (HTML injection / render breakage)
- **Module/area:** grooming | **Confidence:** high
- **Location:** grooming.html renderDaily() card innerHTML line 809 (`${rec.name}`); renderMonthly() row innerHTML line 922 (`${c.name}`)
- **Defect:** Both renderers build card/row HTML with template literals assigned via .innerHTML and interpolate the raw stored name (rec.name / c.name) with no escaping. Names are user-controlled (free-text #cro-inp or employee master). Concrete failing input: save a checklist for a CRO named `<b>A` or `A<img src=x onerror=alert(1)>` — in Daily Summary the card markup breaks (unbalanced tag bleeds into siblings) and the onerror form executes script. The datalist option (L623) and other spots escape quotes, but these two render paths do not, so the value round-trips into live HTML.
- **Evidence:** L809 `<div class="cro-info-name">${rec.name}</div>` inside card.innerHTML; L922 `...${c.name}</div>` inside tr.innerHTML; contrast L623 which DOES .replace(/"/g,'&quot;') for the datalist.
- **Impact:** A malformed name breaks the layout of the daily/monthly cards (non-fatal but visibly corrupt), and an onerror/script-bearing name runs arbitrary JS in the module iframe. Single-user offline app limits blast radius, but it is a genuine stored HTML-injection / render-corruption bug.
- **Fix hint:** Escape the name before interpolation with a small helper (esc(s)=String(s).replace(/[&<>"']/g,c=>({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;','\'':'&#39;'}[c]))) and use ${esc(rec.name)} / ${esc(c.name)}; also escape i.label for safety even though labels are currently static. Additive.

## [P2] grm-bug-03 — Floor gate uses the FIRST same-day grooming record, not the latest — 2-per-day design + bus dedup desync
- **Module/area:** grooming (data drives integration-bridge) | **Confidence:** medium
- **Location:** integration-bridge.js produce() lines 110-111 (emit id = d+':'+kk(r.name)); consumed by computeGate() L282-283. Root cause is grooming.html allowing 2 records/day (saveCRO gate L706 blocks only at >=2)
- **Defect:** Grooming explicitly permits up to 2 records per CRO per day (saveCRO L706). The bridge producer emits GROOMING_RESULT with idempotency id `date:name`, so for a given CRO+day only the FIRST record ever emitted reaches the bus; the second is deduped and dropped (emit() L83-94 dedups on type:id, full scan). computeGate (L282) then blocks/clears using that first record's pct. Concrete failing sequence: CRO fails at 40% on the morning check (blocked from floor), then re-checks and passes at 100% later the same day — the 100% record is never emitted, so the gate keeps the CRO BLOCKED all day despite the corrected 100% record. The reverse also holds: pass first (100%) then a later 40% record is ignored and the CRO stays cleared.
- **Evidence:** produce L111: emit(bus,'GROOMING_RESULT',d+':'+kk(r.name),{...pct...}); emit() L85-86 dedups on id → 2nd same-day record never emitted; computeGate L282-283 keys off e.payload.date===d and p.pct.
- **Impact:** Cross-module floor-gate decision (QMS/DSR block banner) is driven by a stale grooming score whenever a CRO has 2 records the same day. A remediated CRO stays wrongly blocked, or a failing re-check is wrongly cleared. Silent — no error surfaces.
- **Fix hint:** This fix belongs in integration-bridge.js (not editable per grooming scope): make the grooming producer emit the AGGREGATE/latest per name/day (e.g. include a record-count or max/last pct in the id, or emit id `date:name:idx` and have computeGate reduce to the latest/lowest per name). Flagging here because grooming's 2-per-day rule is what exposes it; grooming.html itself cannot fix it.

## [P3] grm-bug-04 — Best-Day / Lowest-Day checked-count fraction can point at the wrong record when two records round to the same %
- **Module/area:** grooming | **Confidence:** medium
- **Location:** grooming.html renderMonthly() lines 897-900 (bestRec/lowRec = c.records.find(r=>r.pct===best/low))
- **Defect:** best/low are computed from rounded pct values (r.pct is already Math.round'd at save, L719). bestRec/lowRec are then found via find(r=>r.pct===best). When two of a CRO's records share the same rounded pct but different checked/total (e.g. 19/20 and 20/21 both round to 95%), find() returns the FIRST such record, so the small '19/20' fraction shown next to the Best/Lowest % may not be the record actually at the extreme raw ratio. The headline % is still correct; only the tiny checked/total annotation can mismatch.
- **Evidence:** L889 best=Math.max(...pct); L897 bestRec=c.records.find(r=>r.pct===best)||{}; L899 bestFrac=bestRec.checked+'/'+bestRec.total.
- **Impact:** Cosmetic/edge: the fraction beside Best Day / Lowest Day may show a different record's counts than intended. No wrong headline figure, no data loss.
- **Fix hint:** When multiple records tie on rounded pct, pick the one with the true max/min checked/total ratio for the fraction, or annotate with the tie count. Low priority.

## [P3] grm-bug-05 — Autocomplete 'wait until 5pm for 2nd check' spacing rule is not enforced at save — only hides the name in the datalist
- **Module/area:** grooming | **Confidence:** high
- **Location:** grooming.html grmNameAvailable() line 622 vs saveCRO() gate line 706
- **Defect:** grmNameAvailable() removes a CRO from the datalist after 1 record until new Date().getHours()>=17 (c>=1 && hours<17 → false). But the actual save gate (saveCRO L706) only blocks at >=2 records/day and does NOT check the time. So the intended 'space the two daily checks apart / no 2nd before 5pm' rule is enforced only in autocomplete: a user who simply types the full name manually can save the 2nd record at any time before 5pm. Result is an inconsistent, effectively-unenforced rule rather than a data bug.
- **Evidence:** L622 if(c>=1 && new Date().getHours()<17) return false;  vs  L706 if(__cnt>=2){...return;} (no hour check).
- **Impact:** Minor UX/logic inconsistency: the before-5pm spacing appears enforced (name vanishes from suggestions) but is trivially bypassed by typing. No wrong figure or data loss.
- **Fix hint:** Decide the intended rule and enforce it in ONE place: either drop the hours<17 branch from grmNameAvailable (rely purely on the 2/day cap), or add the same time check to the saveCRO gate so both agree. Additive.
