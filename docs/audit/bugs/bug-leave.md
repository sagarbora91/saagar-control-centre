## [P1] leave-bug-01 — loadData() can leave data.leaves / data.agendas undefined → module crashes to a blank screen on load
- **Module/area:** leave | **Confidence:** high
- **Location:** loadData() lines 861-880 (v3 branch 863-868 only defaults employees; v2-migration branch 871-877 defaults neither leaves nor agendas)
- **Defect:** loadData() returns the parsed leavedesk_v3 object after only ensuring p.employees exists — it never guarantees p.leaves or p.agendas. If the persisted leavedesk_v3 blob is ever partial (a hand-edited backup imported to storage, a truncated write, or any writer that produced {employees:[...]} without leaves), or the app migrates from a leavedesk_v2 blob that predates the agendas map, the returned object is missing leaves and/or agendas. renderCalendar() then evaluates data.leaves[key] (line 1321) and renderStats()/openClearConfirm() call Object.values(data.leaves) (lines 1442,2393) on undefined.
- **Evidence:** Node repro: data={employees:[]} → `data.leaves[key]` throws "Cannot read properties of undefined (reading '2026-07-03')"; `Object.values(data.leaves)` throws "Cannot convert undefined or null to object". v3 branch (866) only does `if(!p.employees)p.employees=[]`; v2 branch (875) only sets `p.employees=[]`.
- **Impact:** Module throws 'Cannot read properties of undefined' during renderCalendar()/renderStats() at startup and renders a blank/broken calendar. Owner sees an empty, non-functional Leave module. Reproduced in Node: with data={employees:[]}, data.leaves[key] throws and Object.values(data.leaves) throws.
- **Fix hint:** In loadData(), after parsing (both the v3 branch and the v2-migration branch), coerce the shape additively before returning: if(!p.leaves||typeof p.leaves!=='object') p.leaves={}; if(!p.agendas||typeof p.agendas!=='object') p.agendas={}; if(!Array.isArray(p.employees)) p.employees=[]; This is additive-only, no storage-core edits, and matches the final-fallback shape already returned at line 879.

## [P2] leave-bug-02 — Leaves/agendas dated before May 2026 are unreachable and unreportable, yet an April-2026 leave still inflates the FY balance shown to the owner
- **Module/area:** leave | **Confidence:** medium
- **Location:** prevMonth() line 1232-1233 + buildMonthJumper() line 1419-1434 (hard floor START_MONTH=4/START_YEAR=2026); fyUsage() line 939-951; openReport() per-month scan line 2104-2118
- **Defect:** Calendar navigation and the month jumper are hard-floored at May 2026. importJSON()/isValidDateKey() accept ANY valid non-weekend date, so a backup can inject leaves for e.g. April 2026 or earlier. Those rows can never be shown on the grid (prevMonth() returns early at the floor and buildMonthJumper() starts at the floor) and never appear in the monthly report (openReport scans only the currently-viewed month). However fyRangeOf()/fyUsage() window the Indian FY as April-1→March-31, so an April-2026 approved leave IS inside FY2026-27 and is summed into the 'used X of Y this FY' figure shown in the Add-Leave balance hint (line 1765) and the report's FY Balance column (line 2162).
- **Evidence:** prevMonth() line 1233 `if(currentYear===START_YEAR&&currentMonth===START_MONTH) return;`; buildMonthJumper() line 1423 starts at `y=START_YEAR,m=START_MONTH`; fyRangeOf() line 934 sets from `${s}-04-01` where s=year for month>=3, so April is in-FY; fyUsage() line 942 only filters by the FY window, not by the navigable range.
- **Impact:** Owner sees an FY leave-balance 'used' figure (e.g. 'Casual Leave: used 3 of 12') that includes leave days they cannot see, locate, or delete anywhere in the UI. The only remedy is Clear All. Confusing balance discrepancy; possible over-count of an employee's consumed quota with no visible source row.
- **Fix hint:** Either (a) reject import date-keys earlier than the START_YEAR/START_MONTH floor in importJSON (add `if(k < dateKey(START_YEAR,START_MONTH,1)) {skipped++; return;}` alongside the existing weekend/validity checks), so no unreachable rows can be created; or (b) let prevMonth()/buildMonthJumper() extend back to the earliest date-key actually present in data.leaves/data.agendas so any stored leave is reachable and deletable. Additive/localStorage-safe.

## [P2] leave-bug-03 — Approved leave dated more than 7 days in the past never reaches payroll (LEAVE_APPROVED never emitted for it)
- **Module/area:** leave (cross-module with integration-bridge.js) | **Confidence:** medium
- **Location:** integration-bridge.js produce() line 136 `if(String(dk).slice(0,10)<rc) return;` (rc=cutoffIso(RECENT_DAYS=7)); leave.html decideLeave() line 1011-1027 sets status='approved' with no re-emit path
- **Defect:** The bridge producer only scans leave date-keys within RECENT_DAYS (7) of today when emitting LEAVE_APPROVED. A leave whose DATE is older than 7 days — a back-dated leave imported/created for last month, or a leave the owner approves late (the Approvals modal at line 796-800 explicitly warns 'Decide within 7 days of the leave date') — will have status:'approved' in leavedesk_v3 but its date-key is < rc, so produce() skips it and no LEAVE_APPROVED event is ever emitted. consumeAttendanceFeed() therefore never buckets it into saagar_payroll_attendance_feed.
- **Evidence:** integration-bridge.js line 136 skips `dk<rc`; line 137-139 only emits for `l.status==='approved'` (or legacy no-status). Node: cutoffIso(7) on 2026-07-03 = 2026-06-26, so any leave dated <=2026-06-25 is skipped.
- **Impact:** That approved absence silently never appears in the payroll attendance feed for the affected employee/month, so the payroll maker can over-pay (counts a present day where the employee was on approved leave). This is an owner-facing figure gap. It is documented in the UI note, so it is a known limitation rather than a silent defect, hence P2 not P0.
- **Fix hint:** No safe fix inside leave.html alone (the window lives in the bridge, and RECENT_DAYS bounding is deliberate to avoid re-flooding the bus). Best module-side mitigation: surface the constraint at decision time — when decideLeave() approves a leave whose key is older than ~7 days, show a warning toast that it will not auto-sync to payroll and must be entered manually. Any change to the bridge scan window is out of scope for this read-only leave audit and must not touch storage-core.

## [P3] leave-bug-04 — Bridge-seeded staff show 'No ID' in Staff Master due to employeeId vs empId field-name mismatch
- **Module/area:** leave (cross-module with integration-bridge.js) | **Confidence:** high
- **Location:** leave.html renderEmpList() line 2033 reads emp.empId; addEmployee() line 2076 writes empId; integration-bridge.js reconcileMasters() line 550 writes employeeId
- **Defect:** When the bridge auto-seeds the central Employee Master into Leave's data.employees, it creates records shaped {id, name, employeeId:e.empId||'', department:e.dept||''} (bridge line 550). Leave's own addEmployee() instead stores the ID under empId (line 2076), and renderEmpList() reads emp.empId (line 2033) for display. So a bridge-seeded employee's ID is under the wrong key and renders as 'No ID / department' even though the central master had an employee ID.
- **Evidence:** leave.html:2076 `data.employees.push({ id: uid(), name, empId: id, department: dept })`; leave.html:2033 `([emp.empId, emp.department]...)`; integration-bridge.js:550 `...employeeId:e.empId||'',department:e.dept||''`.
- **Impact:** Cosmetic only: the Staff Master row shows 'No ID' for auto-seeded employees. Name-keyed leave tracking, balances, and the leaveName dropdown all work correctly because they key on name/id, not empId. No data loss.
- **Fix hint:** In leave.html renderEmpList() (line 2033) read a fallback: use `emp.empId || emp.employeeId` when composing the meta line, so bridge-seeded records display their ID. Additive, read-only, no storage-core change.

## [P3] leave-bug-05 — getInitials()/getAvatarColor() throw on a leave or employee row with a missing name
- **Module/area:** leave | **Confidence:** medium
- **Location:** getAvatarColor() line 1136-1137 (name.length/charCodeAt) and getInitials() line 1141-1142 (name.split); callers renderCalendar() line 1532, openDayModal() line 1538, renderEmpList() line 2023
- **Defect:** getAvatarColor() dereferences name.length/name.charCodeAt and getInitials() calls name.split(' ') with no null guard. In-app writers always supply a name and importJSON() rejects rows with empty name, so this is only reachable via a corrupt/hand-edited leavedesk_v3 blob containing a leave/employee whose name is missing or non-string. Such a row makes renderCalendar() throw at getAvatarColor(l.name) (line 1532), breaking the whole grid render.
- **Evidence:** line 1137 `for(let i=0;i<name.length;i++) h=(h<<5)-h+name.charCodeAt(i)`; line 1142 `name.split(' ')` — neither coerces name; renderCalendar line 1532 `const color=getAvatarColor(l.name)`.
- **Impact:** A single malformed stored row (name undefined) crashes calendar rendering — module goes blank. Low likelihood because normal write paths guarantee name; only corrupt storage triggers it.
- **Fix hint:** Guard both helpers: `function getInitials(name){name=String(name||'');...}` and `function getAvatarColor(name){name=String(name||'?');...}`. Additive, no storage-core change.
