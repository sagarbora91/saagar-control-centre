## [P1] exp-bug-01 — Ledger edit/void races the bridge's 60s tick → synced income silently lost (whole-blob last-write-wins)
- **Module/area:** expense | **Confidence:** medium
- **Location:** expense.html editEntry() line 759+773 and voidEntry() line 779+788 (saveLedger of stale getLedger() array); collides with integration-bridge.js consumeServiceIncomeToLedger() line 426-449 which appends WSC income to gm_expenses
- **Defect:** editEntry()/voidEntry() call led=getLedger() when the modal OPENS, the user then reads/types for an arbitrary time, and on Confirm the ENTIRE stale array is written back via saveLedger(led). The bridge tick (TICK=60000ms) independently loads gm_expenses, appends a SERVICE_DELIVERED income row, and writes it back. Repro: open Edit on any entry, wait for the ~60s bridge cycle to post a wsc_<id> income row (or a QMS/stock sync), then click Confirm. The confirm write clobbers the whole blob with the pre-tick snapshot, permanently dropping the bridge-posted income row. Same class: postSrc() (line 1109-1114) reads feedItems() then appends+saves the whole blob, so a near-simultaneous bridge post or a double-click can duplicate a sourceRef (both writers saw it unposted). No re-read/merge before write in either path.
- **Evidence:** editEntry: var led=getLedger()... (modal opens) ...e.amount=num(val('m_amt'));... saveLedger(led); — full-array write. bridge: arr=Array.isArray(cur)?cur:[]; ... arr.push({...}); if(added){ S(EXP_LEDGER,arr); } — independent full-array write to the same key gm_expenses.
- **Impact:** Real money data loss: cross-module income (WSC service delivered / QMS sale) posted by the bridge disappears from the ledger, understating income and P&L shown to the owner and fed to the Tax feed. Duplicate-post variant overstates income.
- **Fix hint:** In editEntry/voidEntry/approveEntry, re-read getLedger() inside the confirm callback and mutate the entry found by id in the FRESH array (not the array captured when the modal opened), then save. In postSrc, re-derive posted-refs from a fresh getLedger() immediately before pushing and skip any ref already present. Additive only; no storage-core changes.

## [P1] exp-bug-02 — editEntry accepts negative/zero amount (no >0 guard) → wrong money figures in totals, cash statement and tax feed
- **Module/area:** expense | **Confidence:** high
- **Location:** expense.html editEntry() confirm callback, line 771 (e.amount=num(val('m_amt'))) — no validation, unlike addEntry() line 741
- **Defect:** addEntry() rejects amt<=0 ('Enter an amount greater than 0'), but editEntry() has no equivalent check. Repro: create a valid ₹500 expense, click Edit, set Amount to -500 (or 0), enter a reason, Confirm. num() returns the negative value verbatim and it is saved. A negative expense then behaves as income to the cash/P&L math (expTot subtracts a negative, inflating net), corrupts computeDay expectedClosing, the dashboard Month P&L, per-firm P&L, budgets 'actual', and genTaxFeed income/expense/GST totals.
- **Evidence:** line 771: e.amount=num(val('m_amt')); e.category=... — no bounds check; contrast line 741: if(amt<=0){ toast('Enter an amount greater than 0','err'); return; }
- **Impact:** Owner sees wrong income/expense/net and a wrong cash-in-hand expectation; the locked Tax feed for the CA can be generated from corrupted figures.
- **Fix hint:** In editEntry's confirm callback, validate the new amount the same way addEntry does: var na=num(val('m_amt')); if(na<=0){ toast('Enter an amount greater than 0','err'); return false; } before assigning e.amount. Additive.

## [P2] exp-bug-03 — setBudget writes to the wall-clock month, not the month being viewed → budget saved under wrong month
- **Module/area:** expense | **Confidence:** medium
- **Location:** expense.html setBudget() line 1054 (var m=ym(todayStr())) vs renderBudget() line 1037 (var m=ym(asOf()))
- **Defect:** renderBudget() displays and reads budgets for m=ym(asOf()) (the shell-selected view month) and the per-row input's onchange calls setBudget(c,value). But setBudget hard-codes m=ym(todayStr()) — the real current month. The isPast() guard only blocks strictly-past days (asOf()<todayStr()), so when the view-date rail (window.__stAsOf / 'st-date' event) points at a FUTURE date whose month differs from the current month, the Budget tab shows next month's grid, the owner types a cap, and it is silently written into the CURRENT month's budget object (b[currentMonth][cat]) instead of the displayed month. On re-render the value 'vanishes' from the shown month (it was stored elsewhere), and the current month's real budget is overwritten.
- **Evidence:** line 1037: var m=ym(asOf()), ... bm=b[m]||{}; render uses asOf month. line 1054: function setBudget(c,v){ ... var m=ym(todayStr()),b=L(K.budg,{}); b[m]=b[m]||{}; b[m][c]=num(v); — writes current month.
- **Impact:** Budget caps land in the wrong month; owner's near-limit/over alerts and gauges are wrong for both the viewed and the current month. Data desync between what is shown and what is stored.
- **Fix hint:** Make setBudget target the displayed month: var m=ym(asOf()); (matching renderBudget). Keep the isPast() read-only guard. Additive.

## [P2] exp-bug-04 — Per-row getStmt() re-parses the whole statements blob for every ledger row and up to 90× in computeDay → jank/ANR on large seeded data
- **Module/area:** expense | **Confidence:** medium
- **Location:** expense.html ledgerTable() line 698 (getStmt(e.date).closed per row, up to 200 rows) and computeDay() line 558 (getStmt(__wd) up to 90 iterations); getStmt() line 537 does L(K.stmt,{}) = full JSON.parse each call
- **Defect:** getStmt(date) JSON.parses the entire tanishq_statements blob on every call. ledgerTable renders up to __CAP=200 rows and calls getStmt(e.date).closed once per row → up to 200 full-blob parses per ledger render. computeDay's carry-forward walk-back loops up to 90 days calling getStmt(__wd) each time → up to 90 full-blob parses per computeDay, and computeDay runs on the dashboard and cash-statement renders. render() also calls pendingSyncCount()→feedItems() (which iterates all localStorage keys and JSON.parses every matching saagar_stock_*_<date> blob plus a full getLedger()) on EVERY render (tab switch, storage event, st-date event, ~60s bridge-driven storage events). getLedger() itself re-parses and .map(normEntry)s the whole ledger and is called ~19 times across the render paths.
- **Evidence:** line 537: return st[date]||{...} after var st=L(K.stmt,{}); line 698: var dayLocked=getStmt(e.date).closed; (inside rows.map); line 558: for(...__i<90...){ var __s=getStmt(__wd); ... }
- **Impact:** With a large seeded history (many statement days + long no-close gaps + big ledger + many stock-day blobs) each render does hundreds of whole-blob JSON.parses, causing UI freeze on device — the app's historic ANR/crash class.
- **Fix hint:** Read the statements blob once (L(K.stmt,{})) at the top of ledgerTable/renderLedger and pass a closed-set map into the row loop instead of getStmt per row; cache the parsed statements object for the duration of a single computeDay walk-back instead of re-parsing each iteration; memoize getLedger()/feedItems() results per render pass. All additive, no storage-core changes.

## [P2] exp-bug-05 — WSC Sync tab posts finalAmt||estTotal but the bridge only posts finalAmt(>0) under the same ref → estimated amount can lock in as the actual income
- **Module/area:** expense | **Confidence:** medium
- **Location:** expense.html feedItems() WSC branch line 1061-1062 (amt=num((c.delivery&&c.delivery.finalAmt)||c.estTotal)); integration-bridge.js line 178 (wamt=parseFloat(c.delivery.finalAmt); if(!(wamt>0)) return) and line 434-436 (dedupe by ref='wsc_'+cid)
- **Defect:** Both paths dedupe WSC income by the SAME sourceRef 'wsc_<caseId>'. When a closed case has no/zero finalAmt but a positive estTotal, the bridge REFUSES to emit (line 178 requires finalAmt>0), but the Expense Sync tab's feedItems() falls back to estTotal and will post that ESTIMATE as Service Income if the user clicks 'Post to ledger'. Later, when finalAmt is corrected to the true (different) value, the bridge computes the real amount but sees have['wsc_'+cid] already set (posted by Sync with the estimate) and marks the event done without correcting the row (bridge line 435). The ledger keeps the estimated figure forever.
- **Evidence:** expense line 1062: amt=num((c.delivery&&c.delivery.finalAmt)||c.estTotal) with ref='wsc_'+c.id. bridge line 178: var wamt=parseFloat(c.delivery.finalAmt); if(!(wamt>0)) return; — never emits on estimate-only.
- **Impact:** Service income can be recorded at an estimated value that never reconciles to the actual collected amount; income/P&L/tax feed carry a wrong figure for that case.
- **Fix hint:** Align the Sync tab with the bridge contract: in feedItems() WSC branch require a real delivery.finalAmt>0 (drop the estTotal fallback) so the manual and automatic paths agree on the amount for a given wsc_ ref. Additive.

## [P3] exp-bug-06 — Ageing bucket label '60+' actually covers 61+ days (off-by-one label vs boundary)
- **Module/area:** expense | **Confidence:** high
- **Location:** expense.html udBucket() line 1208 (d<=30?'0–30':(d<=60?'31–60':'60+')) with udDaysSince() line 1206
- **Defect:** udBucket puts d<=60 into '31–60' and only d>60 into '60+'. So a receivable exactly 60 days old is in 31–60 (correct), but the '60+' label starts at 61, not 60 as the label implies; likewise the '0–30' label is inclusive of 30 which is fine. Purely a labelling imprecision — the summary buckets in renderUdhaar are internally consistent (each receivable counted once), so no double count and no wrong total.
- **Evidence:** line 1208: return d<=30?'0–30':(d<=60?'31–60':'60+'); day 60 → '31–60', so '60+' == 61+.
- **Impact:** Cosmetic: the '60+' ageing bucket header is off by one day from what it contains; no financial miscalculation.
- **Fix hint:** Either relabel the third bucket '61+' or change the boundary to d<60 for the middle bucket so '60+' includes day 60. Trivial, additive.
