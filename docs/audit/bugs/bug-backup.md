## [P1] bug-backup-1 — Restore rejects saagar_invoice_seq_v1 (a plain number) because the service validator demands an array — counter is dropped, new/restored device reissues DUPLICATE invoice numbers
- **Module/area:** service / restore | **Confidence:** high
- **Location:** index.html:5213 (validateRestoreKeyValue owner==='service') vs storage value written at service module ~line 3625 as String(seq)
- **Defect:** saagar_invoice_seq_v1 is stored as a BARE integer string (e.g. "42"), confirmed by the project's own audit evidence: `let seq = parseInt(localStorage.getItem('saagar_invoice_seq_v1')||'0',10); ... c.invoiceNo='WS-'+year+'-'+String(seq).padStart(3,'0')`. It IS in STORAGE_RULES.service.exact so it exports fine. But on restore, restoreKeyOwnerId returns 'service' (not 'control', so the control-key bypass at 5205-5210 does not apply), and validateRestoreKeyValue line 5213 does `return {ok:Array.isArray(parsed)}` for ALL service keys. parsedRestoreValue("42")=42, Array.isArray(42)=false -> {ok:false} -> pushed to result.invalid -> the key is NOT written back. The round-trip silently drops the invoice counter.
- **Impact:** After a restore or full migration to a new phone, the invoice sequence resets to '0'. The service module then reissues WS-<year>-001, 002... that collide with invoice numbers already printed on delivered customer job cards/proformas. Duplicate customer-facing invoice numbers = billing/audit integrity break; the owner has no signal it happened. This is exactly the additive-key-dropped class the task flagged.
- **Fix hint:** In validateRestoreKeyValue, exempt the two non-array service keys before the array check: `if(owner==='service' && (k==='saagar_invoice_seq_v1'||k==='saagar_wsf_settings_v1')) return {ok:true};` (mirrors the existing gm_role exemption at 5211). Keep the array rule only for saagar_wsf_v2 (the case list). Validator-only change; no storage-core edit, no new key, additive.

## [P1] bug-backup-2 — Restore also rejects saagar_wsf_settings_v1 (an object) under the same 'service must be array' rule — the watch-photo-mandatory policy silently reverts to default on restore
- **Module/area:** service / restore | **Confidence:** high
- **Location:** index.html:5213; key documented in SCHEMA.md:247/464 as object {watchPhotoMandatory:bool}
- **Defect:** saagar_wsf_settings_v1 is a single-blob OBJECT ({watchPhotoMandatory:bool}) per the project's own SCHEMA.md ('array · object' — it is the object). It sits in STORAGE_RULES.service.exact, so owner==='service' and it hits the same line 5213 Array.isArray gate. An object fails Array.isArray -> {ok:false} -> result.invalid -> dropped on restore. Same root cause as finding 1: the service validator was written when saagar_wsf_v2 was the only service key and never updated when Wave-2/3 added two non-array service keys.
- **Impact:** On restore/migration the admin policy 'a case cannot be saved without a received-condition watch photo' is lost and falls back to default, weakening the evidence-capture control the owner deliberately enabled. Silent — no rejected-key surfacing beyond a count.
- **Fix hint:** Covered by the same fix as finding 1 (exempt saagar_wsf_settings_v1 from the array rule). Alternatively broaden line 5213 to accept an object for settings and array for the case list. Validator-only, additive.

## [P2] bug-backup-3 — saagar_bridge_config is not in the backup whitelist — owner-tuned integration thresholds (voucher ₹, fail %, leave gates) are dropped from every backup/restore/migration
- **Module/area:** integration bridge / whitelist | **Confidence:** high
- **Location:** index.html STORAGE_RULES 1923-1935 + appControlKeys 2070 (neither covers it); written integration-bridge.js:42 CFG='saagar_bridge_config', read/used line 492 voucherThreshold
- **Defect:** saagar_bridge_config is the SOLE persistence for the integration rules {failPct, voucherThreshold(default 2000), leaveGates}. It starts with 'saagar_' but matches NO STORAGE_RULES exact/prefix (the only saagar_ prefixes are saagar_stock_/saagar_dsr_/saagar_grooming_) and is NOT in appControlKeys, so isWhitelistedAppKey('saagar_bridge_config') is false. appStorage() filters by isWhitelistedAppKey, so the key is excluded from backupPayload, migration export, AND the pre-factory-reset safety backup. integration-bridge.js line 492 uses voucherThreshold to gate voucher creation.
- **Impact:** After restore or a full migration to the new system, the owner's tuned business rules silently revert to defaults (voucher approval threshold back to ₹2000, fail% back to 60, leave gates re-enabled). No warning. Not a wrong-money-figure, but a silently-lost owner configuration that drives an approval workflow — the 'check for more dropped additive keys' the task asked for.
- **Fix hint:** Add 'saagar_bridge_config' to appControlKeys() (it is app-control state, not a module blob), OR give it its own STORAGE_RULES entry. Then also add a restore validator branch (owner==='control' -> {ok:true} already covers it once whitelisted, since it is not one of the specially-validated control keys). Additive, no storage-core edit.

## [P2] bug-backup-4 — Restore rollback snapshot ignores safeSet failure — a large (3327-key) backup can exceed quota, the rollback is silently NOT saved, then data is overwritten with no undo
- **Module/area:** restore | **Confidence:** medium
- **Location:** index.html:5285 safeSet(rollbackKey,...) return ignored; overwrite proceeds at 5290
- **Defect:** restoreValidatedBackup builds a rollback object holding the PRIOR value of every key being restored, then `safeSet(rollbackKey, JSON.stringify(rollback))` at 5285. safeSet returns false on QuotaExceededError (2064) but the return is discarded. Immediately after, line 5290 overwrites all keys. For a full restore of thousands of keys, the rollback blob roughly DOUBLES the footprint of the restored data at the moment of writing, so on a near-full store the rollback write is the most likely thing to fail — precisely when the user most needs undo. The UI promised 'A rollback snapshot will be saved before any data is replaced' (5258).
- **Impact:** On a large restore near quota, the rollback silently does not persist, then the overwrite runs anyway. If the restored file was wrong/partial, the owner cannot undo — the promised safety net is absent exactly in the large-snapshot case the task called out. No corruption of the restored data itself, hence P2, but it breaks the stated safety guarantee.
- **Fix hint:** Check the safeSet return: `if(!safeSet(rollbackKey, JSON.stringify(rollback))){ if(!confirm('Could not save an undo snapshot (storage full). Restore without the ability to undo?')) { closeModal(); return; } }`. Message must be English. Additive; no storage-core edit.

## [P3] bug-backup-5 — ui_day_closed / ui_hide_amounts / saagar_selected_date / saagar_acting_as / saagar_ui_mode are excluded from backup by the whitelist (benign, but confirms the manifest's 'every key' claim is inaccurate)
- **Module/area:** whitelist / migration manifest | **Confidence:** high
- **Location:** index.html EOD_CLOSED_KEY 2920, ui_hide_amounts 3012, SELECTED_DATE_KEY 2022, ACTING_AS_KEY 2861, UI_MODE_KEY 6681; whitelist 1923-2072
- **Defect:** These persisted keys are not in STORAGE_RULES nor appControlKeys, so isWhitelistedAppKey drops them from backup/migration. Unlike findings 1-3 the lost state is ephemeral UI/session (today's EOD tick, amount-hide toggle, viewed date, acting-as impersonation, mobile/desktop layout) and self-heals, so losing it on restore is acceptable — arguably correct (you would not want a stale ui_day_closed or saagar_acting_as to travel to a new phone). Flagged only because the migration manifest text/comments imply a complete key set ('EVERY storage key', keyInventory over 'totalKeys') while these are silently outside the count, and because it documents that the whitelist-only design is the mechanism that also caused finding 3.
- **Impact:** No data loss of business value. Cosmetic reset of preferences after restore. Manifest key inventory undercounts device state, which a rebuild importer should be aware of.
- **Fix hint:** No code change required for the ui_*/session keys (dropping them is desirable). If exhaustive fidelity is wanted for the layout preference only, add saagar_ui_mode to appControlKeys. Otherwise document in the manifest that ephemeral ui_*/session keys are intentionally excluded.
