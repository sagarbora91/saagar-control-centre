## [P1] bridge-01 — reconcileEmployeeMaster writes the QMS blob (S(QMS,q)) — read-modify-write lost-update race that can wipe an in-flight QMS session
- **Module/area:** bug | **Confidence:** medium
- **Location:** integration-bridge.js — reconcileEmployeeMaster(), lines 525-528 (q=L(QMS); q.cros.push(...); S(QMS,q))
- **Defect:** On every cycle (60s tick, storage event, and iframe-load) reconcileEmployeeMaster does q=L(QMS) at 525, appends any Employee-Master name missing from q.cros, then S(QMS,q) at 528. QMS runs in an iframe and (per this file's own comments at 258-264 and 524) keeps its ENTIRE state in memory and saves it wholesale, never re-reading storage. If QMS saves (a new customer, an audit, an allocation) between the bridge's L(QMS) read and its S(QMS,q) write, the bridge overwrites the QMS key with a STALE full blob and silently loses whatever the SM just entered. The _running re-entrancy lock does NOT protect this: the collision is cross-context (bridge in the shell page vs QMS in the iframe both writing the same localStorage key), not re-entrant. This directly contradicts the invariant the file states elsewhere ('The bridge must NEVER write into the QMS blob... a bridge-written field would be clobbered by the next QMS save').
- **Evidence:** line 525: var q=L(QMS,null); ... line 528: if(add){S(QMS,q);blog('seeded '+add+' → QMS roster');}  — vs the file's own rule at 259-261: 'The bridge must NEVER write into the QMS blob: QMS keeps its whole state in memory and saves it wholesale ... so a bridge-written field would be clobbered by the next QMS save'
- **Impact:** Silent QMS data loss (a just-added customer / audit / allocation vanishes) whenever a new employee was added in Settings→People AND a QMS save lands in the read-write window. Rare timing but real, and the loss is invisible until the SM notices missing rows.
- **Fix hint:** Do not seed the QMS roster by rewriting the whole QMS blob. Either (a) drop the S(QMS,q) roster-seed entirely and let QMS union the Employee Master at its own read time (the same pattern the file already uses for Stock brands via getBrands unioning the master), or (b) write the roster additions to a SEPARATE additive key (e.g. saagar_qms_roster_seed) that QMS reads and merges, never touching retail_queue_management_v1. Additive localStorage only; do not touch storage-core/sqlite/photo-store.

## [P2] bridge-02 — consumeAttendanceFeed / croAuditFeed bucket by case-preserving name (nm) so mixed-case names across modules split into duplicate buckets
- **Module/area:** bug | **Confidence:** medium
- **Location:** integration-bridge.js — consumeAttendanceFeed slot(...,nm(p.name)) lines 356 & 362; producers emit nm(name) from two different modules (DSR staffName line 145, LeaveDesk staffName line 138)
- **Defect:** The attendance feed keys each person's monthly bucket by nm(p.name) — trimmed but NOT lowercased (line 348-352 slot()). The DSR_SUBMITTED name comes from the DSR record's staffName (line 145) and the LEAVE_APPROVED name comes from LeaveDesk's staffName (line 138); these are independent modules with independent free-text/casing. If the same employee is stored as 'Amit Kumar' in DSR and 'amit kumar' in LeaveDesk (or with different internal spacing), consumeAttendanceFeed creates TWO separate buckets, so payroll sees that person's present-days under one spelling and leave-days under another, under-counting each. computeGate correctly dedupes case-insensitively via kk() (lines 283/289), which makes the attendance feed the outlier. consumeCroAuditFeed keys by kk() (line 380) yet then re-reads dsrKey(p.date,p.name) with the raw p.name — consistent within itself but inconsistent with the attendance feed's nm() keying.
- **Evidence:** line 356: var o=slot(String(p.date).slice(0,7),nm(p.name)); line 362: var o=slot(String(p.date).slice(0,7),nm(p.name));  slot uses feed[em][name] with name=nm(...) — no lowercasing, unlike kk() used in computeGate seen[kk(p.name)] and consumeCroAuditFeed slot(...,kk(name))
- **Impact:** Payroll attendance/leave totals split across case-variant name buckets for any employee whose name casing/spacing differs between DSR and LeaveDesk — silent under-count of present-days and leave-days feeding the payroll maker.
- **Fix hint:** Key the attendance bucket by kk(p.name) (lowercased) like computeGate/croAuditFeed do, and carry a display name field inside the bucket object (e.g. o.display=nm(p.name)) for rendering. Additive/in-memory change only.

## [P2] bridge-03 — computeGate puts half-day-leave staff into blocked[] as a full floor block; the red floor-gate banner then bars them all day
- **Module/area:** bug | **Confidence:** medium
- **Location:** integration-bridge.js — computeGate() line 288-289 (LEAVE_APPROVED → blocked.push({why:'on leave'})); banner render gateBanner() lines 686-702
- **Defect:** LEAVE_APPROVED events carry type (full_day/half_day), emitted at line 139 (type:l.type||'full_day'). The 'unavailable' map (line 295) correctly distinguishes half-day ('half day', leave:true) from full-day. But the blocked[] array (line 288-289) pushes EVERY LEAVE_APPROVED-today into blocked with why:'on leave' regardless of type, and blocked[] is exactly what drives the red fixed floor-gate banner in QMS/DSR ('Do not assign / expect on floor until resolved', lines 692-694). So an employee on HALF-day leave is shown as fully blocked from the floor for the entire day.
- **Evidence:** line 288-289: if(e.type==='LEAVE_APPROVED' && e.payload && e.payload.date===d){ var n=e.payload.name; if(!seen[kk(n)]){ blocked.push({name:n,why:'on leave'}); ... }  — type is never checked here, whereas line 295 unavailable[] does check lt==='full_day'
- **Impact:** Staff on half-day leave are wrongly presented as fully unavailable in the floor-gate banner, so the SM may avoid assigning them for the half of the day they are actually present. Incorrect gating, workaroundable by ignoring the banner.
- **Fix hint:** In computeGate, only push full_day leave into blocked[] (e.g. if((e.payload.type||'full_day')==='full_day')); leave half-day staff to the unavailable map only, or label them 'half day' in blocked[].why so the banner text distinguishes. In-memory logic change only.

## [P2] bridge-04 — customer_master names[] dedup is case-sensitive, so case/spacing variants of one name fill the 6-name cap and can crowd out genuinely distinct names
- **Module/area:** bug | **Confidence:** high
- **Location:** integration-bridge.js — reconcileMasters() touchCust(), lines 587-590 (e.names.indexOf(nn)<0 && e.names.length<6)
- **Defect:** The derived customer identity index (saagar_customer_master_v1) dedupes each mobile's names[] with e.names.indexOf(nn)<0 where nn=nm(name) — trimmed but NOT case-normalised. If the same customer is written as 'Ravi' in QMS and 'RAVI' in Service (or 'Ravi ' vs 'ravi'), both accumulate into names[]. With the hard cap of 6 (e.names.length<6), repeated case-variants of a single name can consume the cap and prevent a genuinely different associated name (e.g. a spouse sharing the mobile) from ever being recorded. The mobile-keyed identity itself stays correct (norm10 last-10-digit keying is sound), so this only pollutes the display-name list feeding Customer 360.
- **Evidence:** line 589: var nn=nm(name); if(nn && e.names.indexOf(nn)<0 && e.names.length<6){ e.names.push(nn); cmCh=true; }  — indexOf is exact-string, so 'Ravi' and 'RAVI' are treated as distinct and both stored
- **Impact:** Customer 360 name display for a mobile can show duplicate case-variants and, at the 6-name cap, drop a legitimately distinct name. Cosmetic-to-minor data-quality issue; identity/repeat-flag still works.
- **Fix hint:** Dedup names case-insensitively (compare kk(nn) against kk of existing entries) before pushing, keeping the first-seen display casing. Purely additive/in-memory.

## [P3] bridge-05 — consume() swallows handler exceptions, so a persistently malformed event is re-attempted every single cycle until it prunes out
- **Module/area:** bug | **Confidence:** medium
- **Location:** integration-bridge.js — consume() line 101 (try{...}catch(err){}) and all consumers built on it
- **Defect:** consume() wraps each handler in try/catch and, on throw, neither marks the event consumed nor counts it — it is retried every cycle. Most handlers guard their payload shape (return true on missing fields → consume-and-drop), but any unguarded throw inside a handler (e.g. an unexpected non-string in a field that reaches .slice on a number is coerced by String() so safe, but a genuinely malformed nested object could throw) causes that event to be re-processed on every 60s tick and every storage event until busPrune ages it out (up to BUS_TTL_DAYS=14). This is wasted work, not data loss, since deterministic ids prevent double-application on the paths that DO succeed.
- **Evidence:** line 101: try{ if(fn(e)!==false){ e.consumed[who]=true; _busDirty=true; n++; } }catch(err){}  — catch is empty; a throwing fn leaves e.consumed[who] unset → retried next cycle
- **Impact:** Minor, bounded perf churn on malformed events for up to 14 days; no correctness or data-loss impact given the prune ceiling and the many explicit shape guards already present.
- **Fix hint:** Optionally mark an event consumed after N failed attempts (store a small attempt counter on the event) so a poison event stops being retried; or tighten per-handler guards. Not urgent given the prune bound.
