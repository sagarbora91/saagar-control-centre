## [P2] bug-planning-01 — QMS actual-sales attribution uses UTC date from closedAt, mis-dating early-morning IST sales at festival window edges
- **Module/area:** planning | **Confidence:** medium
- **Location:** planning.html — actualFor(), line 82 (var d=String(c.closedAt||c.exitTime||c.entryTime||'').slice(0,10))
- **Defect:** QMS writes closedAt/exitTime/entryTime as new Date().toISOString() (UTC) — confirmed in qms.html confirmCloseLead (c.closedAt=new Date().toISOString()) and markExit. actualFor derives the sale's date by slice(0,10) of that UTC ISO string, then compares d>=start && d<=end against the festival's local YYYY-MM-DD <input type=date> bounds. In IST (UTC+5:30), any Purchase closed between 00:00 and 05:29 local time gets a UTC date one calendar day EARLIER. A sale legitimately closed at ~01:00 IST on the festival's start date therefore carries the prior UTC date, falls just before 'start', and is EXCLUDED from the 'Actual (QMS sales)' money figure shown to the owner (undercount). Interior multi-day festival days are unaffected (a one-day shift still lands inside the window); only the first day's early-morning sales at the start boundary are dropped. The app's canonical 'today' is LOCAL (todayIso / dsr.html getFullYear+getMonth+getDate), so this UTC slice is inconsistent with the rest of the app's date-key convention. Concrete repro: festival start=2026-11-08; a Purchase of Rs 50,000 closed 2026-11-08 01:30 IST has closedAt='2026-11-07T20:00:00Z', d='2026-11-07' < '2026-11-08' → excluded; owner sees Actual short by Rs 50,000.
- **Evidence:** planning.html:82 `var d=String(c.closedAt||c.exitTime||c.entryTime||'').slice(0,10)` vs qms.html:557 `c.closedAt=new Date().toISOString()` and dsr.html:1385 local-date builder used as canonical today.
- **Impact:** Owner-facing money figure (Actual QMS sales vs target, and % of target / progress bar) can be understated for early-morning sales on the festival's first day. Bounded to the 00:00–05:30 IST window at the start boundary, so magnitude is limited, but it is a wrong money figure shown to the owner. Read-only display; no data corruption.
- **Fix hint:** Derive the local date from the timestamp instead of slicing the UTC ISO string: parse via new Date(c.closedAt) and build YYYY-MM-DD from getFullYear()/getMonth()/getDate() (a local-date helper mirroring todayIso), then compare to start/end. Purely additive read-side change in planning.html; do not touch QMS or storage-core.

## [P2] bug-planning-02 — actualFor re-parses the entire QMS blob and linear-scans all customers once per festival on every render (ANR risk with heavy seeded data)
- **Module/area:** planning | **Confidence:** medium
- **Location:** planning.html — actualFor() line 79-84 called from render() line 134 inside fests.map
- **Defect:** render() maps over every festival and calls actualFor(f.start,f.end) per festival; actualFor calls L(QMS,null) which does a full JSON.parse of retail_queue_management_v1 AND a full arr.forEach scan of q.customers — every time, for every festival, with no memoization. With N festivals and a large seeded QMS blob (thousands of customers), each render() performs N whole-blob JSON.parse bursts + N O(customers) scans. render() runs on initial boot and after EVERY checklist add/toggle/delete (addChkItem/toggleChk/delChk all call render()), so toggling a checkbox re-parses the whole QMS blob N times synchronously on the main thread. This matches the app's documented historic crash class (whole-blob JSON.parse bursts / srcdoc boot cost). Concrete state: 6 festivals + a QMS blob of 5,000 seeded purchase customers → each checklist toggle = 6 full parses + 30,000 iterations synchronously.
- **Evidence:** planning.html:134 `var act=actualFor(f.start,f.end);` inside `fests.map(...)`, and actualFor:81 `var q=L(QMS,null)` (JSON.parse) + `arr.forEach(...)` full scan; render() re-invoked by addChkItem/toggleChk/delChk (lines 119-121).
- **Impact:** Main-thread jank / potential ANR on low-end devices with large seeded QMS data, especially on repeated checklist interactions. Bounded because festival counts are typically small (single digits), so severity is moderate not fatal.
- **Fix hint:** Parse QMS once per render: read L(QMS,null) a single time at the top of render() and pass the customers array (or a prebuilt purchases list) into a version of actualFor that takes the array. Purely additive refactor within planning.html; no storage changes.

## [P3] bug-planning-03 — Festival list is sorted twice; the first sort (line 125) is dead work fully overridden by line 128
- **Module/area:** planning | **Confidence:** high
- **Location:** planning.html — render() lines 125 and 128
- **Defect:** render() sorts fests by start (line 125), then immediately re-sorts the same array by (past-flag, start) on line 128. The line-128 comparator already uses String(a.start).localeCompare(String(b.start)) as its tiebreaker, so the line-125 sort has zero effect on the final order — it is pure wasted work on every render. Not a correctness bug; final ordering is correct.
- **Evidence:** planning.html:125 `.sort(function(a,b){ return String(a.start).localeCompare(String(b.start)); })` immediately followed by planning.html:128 re-sort with same tiebreaker.
- **Impact:** Negligible performance waste (one extra Array.sort per render). Cosmetic/code-hygiene only.
- **Fix hint:** Delete the line-125 sort; keep only the line-128 sort which fully determines order.
