## Policy decisions

### API-22

The previous owner exception allowing installation on API 22 with a loud plaintext fallback is retired. Build 2.9 enforces `minSdkVersion = 23`, and native production eligibility independently requires Android M/API 23 or newer. API-22 devices cannot install this build.

### BKP-03 destination and key custody

- The owner selects a provider-backed folder once through Android's Storage Access Framework. This is vendor-neutral: Google Drive, OneDrive, or another document provider can be used.
- Built-in external-storage, Downloads, and Media document authorities are rejected because they are still on-device.
- The persisted provider URI remains in native Android preferences. JavaScript receives only a SHA-256 destination identifier and a safe display label.
- A random 256-bit portable-backup key encrypts scheduled backups with AES-256-GCM.
- Android Keystore protects that key for unattended backups on the enrolled phone.
- The same random key is separately wrapped by the owner's PBKDF2/AES-GCM recovery passphrase envelope. The passphrase is never stored; a replacement phone can recover the backup key from the `.sccbak` file.
- The standing owner export grant is bound to the approved scope and hashed destination. A changed destination, missing grant, disabled export policy, missing PIN, damaged policy/register, or unsafe production-device posture fails closed.

### DAT-02 resolution strategy

The risky whole-storage worker rewrite was not performed without device evidence. Build 2.9 adds permanent timing instrumentation and a real-device acceptance gate around five actual encrypted whole-database saves. The gate records no business content and stores only device-local timing evidence.

Acceptance budgets are:

- five complete saves;
- database export p95 at or below 150 ms;
- visible frame-gap p95 at or below 250 ms;
- total encrypted save p95 at or below 3,000 ms;
- all saves successful and the app responsive throughout.

`db.export()` remains synchronous in the current storage engine. Therefore DAT-02 is resolved by its roadmap outcome criterion only if both required devices pass this gate at the agreed data volume. A failure on either device reopens the worker/storage-engine rewrite; a passing result is not a claim that the export call itself moved threads.

## BKP-03 behavior implemented

- Automatic check after the private on-device backup check at launch, then every six hours while the app is active.
- First active use of a new day creates the daily off-device generation; no repeated copy after a verified copy for that date unless the owner forces one.
- Verified readback SHA-256 and byte count before success is recorded.
- Daily unique copy is written before `latest`, weekly, and monthly aliases.
- Atomic temporary-document promotion where supported, with a verified fallback for providers that cannot rename.
- GFS retention: 7 daily, 5 weekly, and 12 monthly generations.
- Metadata-only export-register entry for every scheduled attempt.
- Thirty-six-hour failure escalation in Backup settings.
- Device-local schedule/configuration keys are excluded from portable backup and restore.

Operational limitation: this is automatic on first app use of the day and during long-running sessions; Android does not run this WebView workflow while the app remains closed. Acceptance should record this explicitly. A closed-app OS background job would be a separate native scheduling expansion.
